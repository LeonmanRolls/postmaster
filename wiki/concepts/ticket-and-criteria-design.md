# Tickets and acceptance criteria that a run can finish

**The question.** Three runs showed a ticket asking for what a run cannot finish. [#202, After the workhorses and after each review round, check for a lane's reach outside its own worktree](https://github.com/brindlewick/postmaster/issues/202) asked for a complete list of what a lane's commands touch, and took nine review rounds. [#252, Cleaning up after a run is one script, with a dry run and clear errors](https://github.com/brindlewick/postmaster/issues/252) asked for a dry run that predicts every refusal of the real run, and each round found one more. [#216, The private-data check is TypeScript run by Bun, and flags little of the project's own code](https://github.com/brindlewick/postmaster/issues/216) had the same hole found again in a later round. On 2026-10-04 [#291, A ticket's acceptance criteria ask only for what a run can finish](https://github.com/brindlewick/postmaster/issues/291) put four rules into the ticket template and the clerk's instructions. They came from those three cases and no reading. This page tests them against what is published and against the project's own record of 21 runs. It was asked for as [#293, Research: how to design tickets and acceptance criteria that a run can finish](https://github.com/brindlewick/postmaster/issues/293).

**Claim.** The four rules restate an old idea, that a requirement must be verifiable, and each bounded form has older names and some support: default deny and allow lists, observing what a system produces, named examples and named interfaces, a named input language. Nothing read says a bounded form is wrong. The sources ask for the rules to be stated differently in places, and the sources and the project's own record together name eleven other ways a criterion can fail to finish or to mean what it says; the best measured is a check that passes while the criterion is false. The project's own record of 21 runs fits the rules and cannot test them: three readers, two of them given only the ticket texts, labelled the 21 tickets, and at least two of the three flagged 9 as asking for something unbounded; those ran a median 5 rounds against 3; and 68% of the severe findings of rounds 4 and later with a logged text sit in a mechanism of one of the four shapes. The count also found that the lane audit's table of severe findings reads low for two runs. Nothing here measures whether a ticket written under the rules is finished sooner.

**Standing: claimed.** Outside work moves no standing here ([the schema](../schema.md)), and the count of 21 runs reads records that were not promoted. It is a count made with controls, and it is suggestive and not a test: the flagged runs already had more severe findings in round 1, which suggests larger or harder changes. What would settle it is at [the end](#what-would-settle-it).

## The answer

### Is it the halting problem?

Partly, and the true part is narrower than the question. Rice's theorem generalises the halting problem: "all non-trivial semantic properties of programs are undecidable" [@articles/wikipedia-rice-theorem/passages.md]. A semantic property is "one about the program's behavior", such as whether it terminates for all inputs, and a non-trivial one is "neither true for every program, nor false for every program". Whether a lane's shell commands ever write outside its folder, or whether a dry run and a real run always do the same, is, by my deduction, a property of that kind. No one procedure decides it exactly for every command, so a ticket that asks for it exactly asks for what no check can give. Each review round then finds another case. That is what [#202](https://github.com/brindlewick/postmaster/issues/202) and [#252](https://github.com/brindlewick/postmaster/issues/252) showed.

Three limits of the theorem matter to someone writing a ticket, and each is in the sources.

- **It is about one procedure for all programs.** Meyer's reading of the same limit: "no general mechanism exists that could examine an arbitrary program or loop and tell us whether it will always terminate", and this "in no way excludes the possibility of verifying (although not through "testing") that a particular program or loop will terminate" [@articles/meyer-ieee830-naivete/passages.md]. A named program is outside it, as Meyer says. So is a restricted class such as finite-state programs, which Wikipedia names as the reach of model checking [@articles/wikipedia-rice-theorem/passages.md]. My reading, not a sentence in a source, is that one run which can be watched is outside it too, because the theorem quantifies over every program and every unbounded run. A watched run shows what that run did and no more: testing is "hopelessly inadequate for showing their absence" [@papers/dijkstra-1972-humble-programmer/passages.md].
- **It allows an answer that may say "maybe".** "It is possible to implement a tool that always overestimates or always underestimates, so in practice one has to decide what is less of a problem" [@articles/wikipedia-rice-theorem/passages.md]. The price of over-approximating is false alarms [@articles/cousot-abstract-interpretation-nutshell/passages.md]; my reading is that the price of under-approximating is misses. My reading: this is the theoretical ground for the template's "it reports it as unknown".
- **It is about programs, not about every input with no end.** A string or a file format is data. For data the limit is different: for complex input languages "full recognition of valid or expected inputs may be UNDECIDABLE" [@articles/langsec-language-theoretic-security/passages.md], and for simple ones my reading is that the difficulty is only that a test cannot cover an unbounded set. My reading is that much of the trouble in a ticket that asks a check to find any private data is not undecidability but an open definition of what counts.

So the halting problem is the right name for shapes 1 to 3 when the open set is programs or commands. For shape 4 it is the wrong name unless the format is itself a complex input language, and it is the wrong name for criteria that rest on an open definition. The practical answers are the same in both cases, and they are old: watch the real run, name a closed set and say "unknown" for the rest, check a bounded set of cases and say how far the bound reaches, and prefer the safe default. Strength: argued, in standards and in a theorem that is proved; the original paper and a textbook statement were not read.

### Do the four shapes and their bounded forms hold?

Nothing read says a bounded form is wrong, and each has older names. No source measured whether a ticket written this way is finished sooner. The strongest evidence for any part is from coding-agent benchmarks, two controlled studies for shapes 1 and 3.

### What the sources add that the rules do not say

1. **The reason given is too broad.** "No tool can decide in general what an arbitrary command or program will do" holds for programs. For complex formats, recognition itself may be undecidable [@articles/langsec-language-theoretic-security/passages.md]; for simple ones my reading is that the reason is size and definition. Meyer makes the same objection to IEEE 830's reasoning [@articles/meyer-ieee830-naivete/passages.md]. A criterion about one named program can be finished by proof or inspection.
2. **"Finite" is not the bar.** A 2002 mailing-list adaptation of IEEE 830's wording defines testable as "some finite cost-effective process" [@articles/w3c-qa-skall-testability/passages.md]; the standard's own text was not read. Recognition must also be "feasible" [@articles/langsec-language-theoretic-security/passages.md]. And agile practice adds a size bound: items "that can be Done by the Scrum Team within one Sprint are deemed ready for selection" [@articles/scrumguides-scrum-guide/passages.md]. A criterion over a finite but huge set, or too much work for one run, fails too.
3. **"Unknown" needs a direction and a cost.** Saltzer and Schroeder's reason for a default of no access is that "some objects will be inadequately considered" [@papers/saltzer-1975-protection/passages.md]. Choosing which error is safer is the author's job. A check that errs toward false alarms costs what it flags: in [#216](https://github.com/brindlewick/postmaster/issues/216) the census flagged 265 lines of the project's own history against the ticket's limit of 50, 255 of them judged made-up, and it still read 236 at the round cap [@trials/2026-10-04-unbounded-criteria-count/results/three-cases.md].
4. **A fifth family of failures is better measured than the four.** A criterion can be finishable and its check can still pass while the criterion is false: 31.08% of one agent's passed patches were suspicious because of weak tests [@papers/aleithan-2024-swebench-plus/passages.md], 345 patches were wrongly marked as passed [@papers/yu-2025-utboost/passages.md], and maintainers would not merge roughly half of the test-passing patches they reviewed [@articles/metr-swebench-passing-prs-not-merged/passages.md]. That is their merge decision, not a finding that the issue was left unsolved. Others are listed under [a fifth shape](#a-fifth-shape-and-more).
5. **A run has no conversation to close the gaps.** Practice from the agile sources closes open points by talking while the work goes on: a story is "not an explicit contract" and its details are co-created [@articles/wake-invest-good-stories/passages.md]. A run of agents cannot. So the written criteria and the ticket's open questions must carry what the conversation would, which makes the four rules matter more for a ticket than for a story. In a controlled study, models that could ask a simulated user improved by up to 74% on under-specified inputs [@papers/vijayvargiya-2025-ambig-swe/passages.md].

### What the project's own record shows

Counted over 21 runs, with controls: [the project's own record](#the-projects-own-record).

- **The rules fit the record, and the record cannot test them.** Three readers labelled each of the 21 tickets, two of them given only the ticket texts, and at least two of the three flagged 9 as asking for something unbounded. Those ran a median 5 rounds against 3, and had 14 severe findings against 3.5 (a rank test gives p of 0.08 and 0.016; a rough guide, possibly confounded by the size or difficulty of the change).
- **Late findings sit in the shapes' mechanisms.** 68% of the 99 severe findings of rounds 4 and later that have a logged text are in a reader of an input it could not list, a difference from a reference, or a forecast of what a command will do, against 38% to 42% in round 1 of the same runs.
- **Wording alone misses the mechanism.** Four of the 12 tickets that fewer than two of the three readers flagged ran past three rounds, with late findings in state and ordering, in a reader of open input or in a parser that had to agree with another.
- **In five runs the user bounded a criterion by hand, after the lanes had started,** each time to one of the four bounded forms. In the four that had reported, the next round had fewer severe findings, which settling down would also show.
- **One control failed.** The lane audit's table of severe findings reads low for [#124](https://github.com/brindlewick/postmaster/issues/124) (28 where the run's own checkpoint lists 94) and for [#109](https://github.com/brindlewick/postmaster/issues/109), so its total of 264 is low by about 70.

### What to change

The proposals are in [the section below](#proposed-changes), each tied to a finding. In short: restate the reason and the bar; name the direction and cost of "unknown", the sampled form, and the split between a "never" instruction and a criterion; restate shapes 2, 3 and 4 (observe or guard, a case that must differ and agreement by construction, a decidable subset); have the clerk read the mechanism and the size of a ticket and not only its words, and ask for a measured number wherever a criterion states one; have a script list the criteria to read as a prompt, never as a verdict; and record at sign-off which criteria were rewritten. [#291](https://github.com/brindlewick/postmaster/issues/291) already made the four rules, the accident-or-hostile line and the clerk's check.

### What could not be shown

No source tested the rules on tickets. The evidence is mostly argued. The controlled studies are on coding-agent benchmarks (shortcuts on impossible tasks, named interfaces, weak tests, clarification, context files), two experiments on how requirements are worded, the accuracy of a smell detector, one maintainers' review and a comparison of shell implementations, with a handful of surveys and one repository's 21 runs. IEEE 830, ISO/IEC/IEEE 29148 and the INCOSE guide were not read in their own words, nor was Rice's paper or a textbook statement of the theorem. A search that found nothing is not proof that nothing exists. The list is in [what was not read](#what-was-not-read-and-what-was-not-found).

## How this was read

**Reading.** On 2026-10-04, in four groups, each by one helper with its own starting points and its own search budget: requirements engineering, agile acceptance criteria and behaviour-driven specifications, formal limits and the practical answers, and specifications for coding agents. The session then read again the pages the answer turns on, tried the sources the helpers could not read, and ran the controls. The record of the search, with every query and what was not read, is a trial: [the search record](../../raw/trials/2026-10-04-criteria-search/method.md) [@trials/2026-10-04-criteria-search/method.md]. It holds 93 searches by the helpers and 6 by the session, 70 fetches by each helper and about 30 by the session, 100 sources read by the helpers and 69 captured in all.

**How entries were chosen.** For "most used", the standards, official documentation, founding texts and widely used tools of each group. For "most serious", the sources with a measurement, and the sources that most directly contradict or qualify the template's rules. Adoption was not counted, so "most used" is a judgement from standing, not a count. A source whose page held nothing on the shapes was left out, except two on the quality of BDD scenarios (Binamungu and others 2020, Oliveira and others 2019), which stay with Shapes `none` as the nearest published work on what makes a scenario good. Each entry in the map names the source, links it, gives the day it was read, which is 2026-10-04 for all of them, and says in one sentence what it says.

**What a quote is worth.** The fetch tool returns a summary written by a small model, and it paraphrases and sometimes contradicts itself between reads. A passage in a capture is marked `checked` only when two separate reads gave it word for word. A quotation of a source comes from a sentence marked `checked` in its capture; words quoted from the ticket template, the clerk's instructions, the trial files or another wiki page are named as such where they occur. A script compared every quotation on the page with the captured passages and with those texts, and none was missing. A page that could not be read is listed under [what was not read](#what-was-not-read-and-what-was-not-found), and nothing is inferred from it.

**How strong.** Each source carries one of the labels the research brief set. `controlled study`: a comparison or a measured outcome. `one report or one team's experience`: a case study, a survey or one company. `argued, not measured`: reasoning, a position, a book or a post with no data. `standard or documentation`: a rule or a description of a tool, which is not evidence that the rule works. `not found`: a search found nothing, and a search that finds nothing is not proof that nothing exists.

**The count of the project's own record** is a second trial: [the count of 21 runs](../../raw/trials/2026-10-04-unbounded-criteria-count/method.md) [@trials/2026-10-04-unbounded-criteria-count/method.md]. It reads the project's run records read-only, with controls. Its counts can be repeated from a run folder with `jq`; its labels and mechanism tags are readers' judgements, and the ticket texts as first received come from the tracker's edit history, or for three runs from the run's own copy.

**Checked by three other readers.** Before the pull request, three readers who had not seen the page's drafting each compared part of its claims with the captures, the records and the template. The first read the answer, the four shapes, the fifth shape and what [#291](https://github.com/brindlewick/postmaster/issues/291) already did, except the record summary: about 330 sentences and table cells. The second read the opening, this section, the map, the proposals and the closing lists: about 225. The third read the record sections and every line changed after the first two readers: about 380. They found 33, 40 and 24 problems, 97 in all: 13 claims that a source or the record contradicted, 11 that said more than it did, 24 that no capture held, and 49 smaller slips. Each was fixed or withdrawn. The last round of fixes was checked against the captures and the trial files, and not by a fourth reader. The quotation script was run after each round.

## The four shapes, one at a time

Each shape below gives what the template says, what supports it, what contradicts it or says it is incomplete, how strong the evidence is, and what the sources do not cover. "My reading" marks a step that is not a sentence in a source.

### Shape 1: "every", "all" or "never" about an input with no end

**The template says:** name the closed set the criterion covers, and say what the check does with anything outside it: it reports it as unknown and fails safe.

**What supports it**

- **The problem has an old name, the negative requirement.** "The objective of a secure system is to prevent all unauthorized use of information, a negative kind of requirement", and "It is hard to prove that this negative requirement has been achieved, for one must demonstrate that every possible threat has been anticipated" [@papers/saltzer-1975-protection/passages.md]. IEEE 830-1998, as Meyer quotes it, calls "the program shall never enter an infinite loop" nonverifiable "because the testing of this quality is theoretically impossible" [@articles/meyer-ieee830-naivete/passages.md]. A page on requirements says the same without a reference: requirements that say the system must never or always exhibit a property "would require an infinite testing cycle" [@articles/wikipedia-requirement/passages.md]. INCOSE's rule R26, as a vendor documents it, tells writers to avoid "unachievable absolutes" such as all, every, always and never [@articles/altium-valiassistant-incose-rules/passages.md].
- **The remedy has the same shape as the template's.** Saltzer and Schroeder: "Base access decisions on permission rather than exclusion", which "means that the default situation is lack of access, and the protection scheme identifies conditions under which access is permitted", because "In a large system some objects will be inadequately considered, so a default of lack of permission is safer". A wrong closed set then fails where it is seen: a mistake in such a mechanism "tends to fail by refusing permission, a safe situation, since it will be quickly detected" [@papers/saltzer-1975-protection/passages.md]. OWASP says the same of input: "Define what the application accepts and reject values outside those rules." and "Do not try to recognize every malicious string." [@articles/owasp-input-validation/passages.md]. An IEEE 802.11 member says it of requirements: "Can we define with precision a sufficiently bounded 'otherwise'?", and if not, "it's not a verifiable statement and IMO should not be stated as a normative requirement" [@articles/rolfe-802-11-negative-requirements/passages.md]. That is the closest wording to the template in the requirements sources, and the only place there where the complement is named.
- **"Unknown" as a legitimate answer.** A monitor that sees a partial observation of a running system gives true, false or inconclusive [@papers/bauer-2011-rv-ltl-tltl/passages.md]. Bounded model checking proves safety "under a given bound", and its unwinding assertion "checks that the loop exit condition is indeed always fulfilled, i.e., the number of unwinding steps was sufficient" [@papers/kroening-2023-cbmc/passages.md]. A shell analyser reports "Can't follow non-constant source" and lets the user name the file or skip it [@articles/shellcheck-sc1090/passages.md]. For graders: "give the LLM a way out, like providing an instruction to return "Unknown" when it doesn't have enough information" [@articles/anthropic-demystifying-evals/passages.md].
- **A measured case for agents.** In ImpossibleBench the tests contradict the specification, so no honest solution passes. GPT-5 passed 54.0% of the conflicting tasks anyway. When models were told to submit a flag string on finding an error, the rate fell "from 54% to 9%" for GPT-5 and "o3 from 49% to 12%", and "the effect is much less pronounced for Claude Opus 4.1" [@papers/zhong-2025-impossiblebench/passages.md]. My reading: the way out has to be an answer the agent is told to give, and it worked unevenly across the three models tested. Spec Kit's version for specs is "Don't guess: If the prompt doesn't specify something, mark it" [@articles/github-spec-kit-r293/passages.md].
- **"Every" over named items is allowed.** INCOSE's R32: "Use "each" instead of "all", "any" or "both" when universal quantification is intended" [@articles/altium-valiassistant-incose-rules/passages.md]. The Definition of Done is "a special set of acceptance criteria" that are "added to every user story" [@articles/cohn-conditions-of-satisfaction/passages.md]; my reading is that this is a bounded "every", over the items of one backlog.

**What contradicts it or says it is incomplete**

- **The word is not the problem.** IEEE 830's own example of a verifiable statement, as Meyer quotes it, says "100% of the time", and the standard says it can be verified "because it uses concrete terms and measurable quantities" [@articles/meyer-ieee830-naivete/passages.md]. INCOSE's R26 names 100% reliability as unachievable. In two full-text reads of the requirements-smells paper by a helper, none of its nine smell definitions named universal quantifiers [@papers/femmer-2017-smells/passages.md], and the part I could read of NASA's list of unverifiable terms has none [@articles/nasa-seh-appendix-c/passages.md]. Both are absences read through a summarising tool, so they are weak. A practitioner guide bans "all", "never" and "always" and gives, as the "Do" example under its tip against "not", "The application must not fail." [@articles/premieragile-acceptance-criteria/passages.md]. My reading: the line is the open set, not the word, and a heading that reads '"Every", "all" or "never"' can be taken as a word ban by a clerk.
- **The reason is stated too broadly.** Meyer's objection to IEEE 830's reasoning is that the halting result concerns "an arbitrary program", and a particular program can be verified [@articles/meyer-ieee830-naivete/passages.md]. The template's "no tool can decide in general what an arbitrary command or program will do" is true in the same way and open to the same objection. A criterion about one named program or one named set can be finished by proof, inspection or a bounded check.
- **"Unknown, fail safe" has a direction and a cost.** Saltzer and Schroeder's safe side is refusal. For an analyser the safe side costs false alarms: over-approximation "leads to false alarms" [@articles/cousot-abstract-interpretation-nutshell/passages.md]. Wikipedia's page on Rice's theorem says it plainly: "it is possible to implement a tool that always overestimates or always underestimates, so in practice one has to decide what is less of a problem" [@articles/wikipedia-rice-theorem/passages.md]. The template says "fails safe" and does not say which way is safe or what a large unknown bucket costs. In [#216](https://github.com/brindlewick/postmaster/issues/216) a census that errs toward false alarms flagged 265 lines against a limit of 50, 255 of them judged made-up [@trials/2026-10-04-unbounded-criteria-count/results/three-cases.md]. What a large team measured about developers' response to false positives (Sadowski and others, at Google) could not be read.
- **A third bounded form is a sample.** A Kiro property is "a universal statement about how your system should behave", and "the tool generates hundreds or thousands of random inputs to try to violate it". The page says "It provides evidence of correctness, not a proof", and "Not every requirement maps cleanly to a property" [@articles/kiro-dev-docs-correctness/passages.md]. This is finishable and says what it shows. The template offers only a closed set; it could add a sample with the count stated and the result worded as evidence.
- **"Never" belongs in two places.** A GitHub post on over 2,500 agent instruction files gives "Ask first" and "Never do" boundaries, with an example "Never do: Modify code in `src/`, edit config files, commit secrets" [@articles/github-blog-agents-md-lessons/passages.md]. A guide by Osmani gives three tiers: "Always do", "Ask first" and "Never do" [@articles/addyosmani-good-spec/passages.md]. Neither says how a run shows it kept the rule. OpenAI's guide lists "Constraints" and "Done when" as separate items [@articles/openai-codex-best-practices/passages.md], and Claude Code's says instructions "are advisory, hooks are deterministic and guarantee the action happens" [@articles/anthropic-claude-code-best-practices/passages.md]. My reading: a "never" belongs in the lane's instructions with a guard that makes it true, and in the criteria only as an observed outcome or a named test.

**Strength.** Standard or documentation, and argued. One controlled study, on three models, supports the "unknown" half for agents. No source measured whether a criterion with a closed set is finished sooner. One experiment measured a wording rule against a later activity: with 41 students, "the use of negative statements did not impact correctness of test cases substantially". A further result of it, "test cases did omit the specified requirement considerably more often", is given in one read as +13% and not significant (p = 0.15) [@papers/mund-2017-quality-matter/passages.md]. Another, with 51 participants, measured readability alone [@papers/winter-2020-quantifiers/passages.md]. A review of 57 publications found 17 that report no impact on any activity [@papers/frattini-2023-quality-theory/passages.md].

**Not covered.** The run-time half of the bounded form, that the check reports anything outside the set as unknown and fails safe, is not found in the requirements or agile sources. No requirements query used those words, and one search of the formal-limits group looked for the idea by name and found no page that names it. It is found in the security and verification sources above, under other names. In the agile sources an unknown goes on a red card, and "A table covered in red (question) cards tells us that we still have a lot to learn about this story" [@articles/wynne-example-mapping/passages.md]; a run has no such conversation. How to choose the closed set so that it is itself complete is not covered either.

### Shape 2: predicting what another program will do

**The template says:** ask for what the check can observe afterwards, such as a changed file, a moved branch or an exit status, and not for a forecast from the program's text.

**What supports it**

- **Behaviour is what the system produces.** Cucumber's reference: "An outcome should be on an observable output. That is, something that comes out of the system (report, user interface, message), and not a behaviour deeply buried inside the system" [@articles/cucumber-gherkin-reference/passages.md]. North: "Acceptance criteria should be executable" [@articles/north-introducing-bdd/passages.md]. Firesmith's checklist: "Does each requirement only specify behavior and/or characteristics that are externally observable when treating the application or component as a black-box?" [@articles/firesmith-good-requirements/passages.md]. EARS writes unwanted behaviour as "If <trigger>, then the <system name> shall <system response>", and the page read shows no "shall not" form [@articles/alistairmavin-ears/passages.md]; my reading is that a check can provoke one named trigger and observe the response.
- **For agents.** "It's often better to grade what the agent produced, not the path it took", because grading the path was found "too rigid and results in overly brittle tests" [@articles/anthropic-demystifying-evals/passages.md]. "The check is anything that returns a signal Claude can read in the conversation: a test suite, a build exit code, a linter, a script that diffs output against a fixture" [@articles/anthropic-claude-code-best-practices/passages.md]. OpenAI's guide: "Done when: What should be true before the task is complete" [@articles/openai-codex-best-practices/passages.md]. SWE-bench Pro writes requirements that "specify the expected behavior but does not prescribe how the solution should be implemented" [@papers/deng-2025-swebench-pro/passages.md].
- **Testing is the right tool for a presence, not an absence.** "Program testing can be a very effective way to show the presence of bugs, but is hopelessly inadequate for showing their absence" [@papers/dijkstra-1972-humble-programmer/passages.md].

**What contradicts it or says it is incomplete**

- **Standards accept some forecasts.** NASA's checklist asks "Can the system be tested, demonstrated, inspected, or analyzed to show that it satisfies requirements?" [@articles/nasa-seh-appendix-c/passages.md]. A 2005 message to a W3C list says "another verification method should be used instead (e.g. analysis, inspection or review of design)" when a requirement is not testable [@articles/boland-w3c-testability-2005/passages.md]. Meyer says a particular program's termination can be verified, though not by testing. So "not for a forecast from the program's text" is stricter than the standards. My reading: a forecast counts when it is a named analysis of a named artifact that says what it cannot follow, as ShellCheck's SC1090 does, and for another program that the check does not control, the criterion should ask for what the check can observe.
- **Afterwards is too late for harm that must not happen.** Saltzer and Schroeder: "Every access to every object must be checked for authority" [@papers/saltzer-1975-protection/passages.md]. My reading: a guard that checks each action does not need to predict the set of actions. In the project's own record, the check in [#202](https://github.com/brindlewick/postmaster/issues/202) ran after a round and could only report a reach; [#200](https://github.com/brindlewick/postmaster/issues/200), whose lane cannot signal a process it did not start because it runs in a process space of its own, took 4 rounds and 7 severe findings, against 9 rounds and 34 for [#202](https://github.com/brindlewick/postmaster/issues/202) [@trials/2026-10-04-unbounded-criteria-count/results/severe-by-round.md]. The tickets differ in size and in kind, so this is a pointer and not a comparison.
- **An observation needs an oracle.** "Without test oracle automation, the human has to determine whether observed behaviour is correct" [@papers/barr-2015-oracle-problem/passages.md]. An exit status or a changed file is an observation; what it must be is the criterion.
- **An observation is one run.** "Never" over runs still needs shape 1's closed set.

**Strength.** Documentation and argued, with one company's report. Nothing measures a ticket's outcome.

**Not covered.** How to bound an observation that is itself a sample of one run. A measured comparison of an agent with a runnable check against one without: not read. Search 17 of the coding-agent record found candidate studies that were never fetched, and the vendors only assert it.

### Shape 3: exact agreement between two implementations of one decision

**The template says:** name the cases that must agree. Any other case may differ, and the output says so.

**What supports it**

- **Specification by example.** Adzic asks for key examples, "a small number of relatively simple scenarios that will be easy to understand, evaluate for completeness and criticise" [@articles/adzic-focus-on-key-examples/passages.md], and says the set is enough "At the point where everyone is happy that they have enough information to work", with "An example demonstrating each important technical edge case" [@articles/adzic-sufficient-set-of-scenarios/passages.md]. Fowler states what that does not give: "Examples only highlight a few points, you have to infer the generalizations yourself" [@articles/fowler-specification-by-example/passages.md]. My reading: a ticket that names cases must also say that other cases are not promised, or each lane will infer its own generalisation.
- **Named interfaces, measured.** SWE-bench Pro: "A common false negative in unit-test verifiers is when a model submits a valid solution with different interfaces than what the unit test is expecting", so "we explicitly define the class and function names". "Without the requirements and interface, both models tested (GPT-5 and Claude Opus 4.1) show significantly degraded performance": 25.9% fell to 8.40% for one and 22.7% to 8.20% for the other [@papers/deng-2025-swebench-pro/passages.md]. This is a controlled study. It shows that pass rates fall when the requirements and the interface are removed together, and the authors explain the fall as false negatives of tests that "expect a narrow set of solutions". It does not show that the failing patches would be accepted by a maintainer.
- **Conformance on named suites.** A formal semantics of the POSIX shell was compared with seven other shells "using three test suites" and found "the most conformant", not equal [@papers/greenberg-2019-posix-shell-semantics/passages.md].
- **What dry-run documentation says.** `make`: "Note that some recipes are still executed, even with this flag", and the exceptions are listed: "recipe lines that begin with '+' characters or contain the strings '$(MAKE)' or '${MAKE}'" [@articles/gnu-make-dry-run/passages.md]. Terraform: "other changes made to the target system in the meantime might cause the final effect of a configuration change to be different than what an earlier speculative plan indicated", so the plan should be re-checked, and a saved plan file can be applied later [@articles/hashicorp-terraform-plan/passages.md]. Helm: "Helm is not supposed to contact the Kubernetes API Server" during a dry run, with `--dry-run=server` as the way to test `lookup` [@articles/helm-lookup-dry-run/passages.md]. Ansible: "Check mode is just a simulation", and "Modules that do not support check mode report nothing and do nothing" [@articles/ansible-check-mode/passages.md].

**What contradicts it or says it is incomplete**

- **The form of the problem.** Exact agreement between two programs is program equivalence, that is, computing the same function as a given program, which is a non-trivial semantic property, so no algorithm decides it for all programs. That is my deduction from the statement of Rice's theorem and not a sentence in a source. The usable form is agreement on named cases.
- **"The output says so" is rarer than the rule says.** `make` lists its exceptions in the manual. Ansible's modules without a check mode report nothing: the output does not say "unknown". Terraform tells the user to check again. None of the four says to print which cases it did not cover.
- **The opposite error sits in the same benchmarks.** SWE-bench+ found that "31.08% of the passed patches are suspicious patches due to weak test cases" [@papers/aleithan-2024-swebench-plus/passages.md], and UTBoost found "345 erroneous patches incorrectly labeled as passed" [@papers/yu-2025-utboost/passages.md]. My reading: a rule to leave other cases free pushes toward looser checks. A ticket needs cases specific enough to fail wrong work and open enough to pass right work. My proposal under [proposed changes](#proposed-changes) is to name at least one case that must differ or be refused.
- **Agreement can be made true by construction.** One function makes the decision and the preview and the real run both call it. Terraform's saved plan and Helm's server-side dry run point that way, and no source I read states it as a rule; practitioner posts on dry-run design were not read. In [#252](https://github.com/brindlewick/postmaster/issues/252) the coachman's own reading at the cap was that "the dry run re-implements every real-run decision inline" [@trials/2026-10-04-unbounded-criteria-count/results/three-cases.md].

**Strength.** One controlled study (the SWE-bench Pro ablation), documentation, and argument. The shell comparison measures shells and not the rule.

**Not covered.** The template's last step, "the output says so": no source says it. Nothing read in the requirements, agile or coding-agent groups is about a dry run and a real run, and search 26 of the coding-agent record found posts on dry-run design that were not read.

### Shape 4: a reader that must handle any format

**The template says:** name the formats it supports, and have it report every other as unsupported.

**What supports it**

- **Name the language and recognise exactly it.** LangSec: "treating all valid or expected inputs as a formal language, and the respective input-handling routines as a recognizer for that language", and "The recognition must be feasible, and the recognizer must match the language in required computation power" [@articles/langsec-language-theoretic-security/passages.md].
- **Fail on the unspecified.** The IETF's critique of liberal acceptance, the robustness principle: "An implementation that reacts to variations in the manner recommended in the robustness principle enters a pathological feedback cycle", and "Choosing to generate fatal errors for unspecified conditions instead of attempting error recovery can ensure that faults receive attention" [@articles/ietf-rfc9413/passages.md]. OWASP: "Reject invalid requests with a clear error; do not continue with partially validated data" [@articles/owasp-input-validation/passages.md]. Default deny is Saltzer and Schroeder's [@papers/saltzer-1975-protection/passages.md].
- **Say what cannot be followed.** ShellCheck's "Can't follow non-constant source" [@articles/shellcheck-sc1090/passages.md]. The shell's power and subtlety "are a dangerous combination" [@papers/greenberg-2019-posix-shell-semantics/passages.md].

**What contradicts it or says it is incomplete**

- **A named format that is itself a programming language is not made finishable by being named.** "For complex input languages the problem of full recognition of valid or expected inputs may be UNDECIDABLE, in which case no amount of input-checking code or testing will suffice" [@articles/langsec-language-theoretic-security/passages.md]. My reading: name a decidable subset, and say what is out.
- **"Unsupported" has to mean something.** RFC 9413 is advice about protocols, and the part I read says to treat unspecified conditions as faults. Whether an unsupported input stops the run or is skipped is a decision for the ticket, and the template does not ask for it.

**Strength.** Documentation and argued. Not searched for in the requirements group, and not found by one agile search or one coding-agent search. No measurement of any rule for shape 4.

**Not covered.** Any agent or benchmark guidance that a reader should report every other format as unsupported: search 25 of the coding-agent record found library documentation about a parser's unsupported-format exception and nothing about agent tasks.

## The project's own record

The record is 21 runs: the 18 of [the lane audit](several-lanes.md) that reached synthesis, and the three the rules were written from, [#202](https://github.com/brindlewick/postmaster/issues/202), [#216](https://github.com/brindlewick/postmaster/issues/216) and [#252](https://github.com/brindlewick/postmaster/issues/252). For each, the count has the review rounds, the severe findings in each round (a verified gating P1 or P2 on a `finding` line), whether its ticket asked for something unbounded, and where its late findings sat. The method, the controls and every table are in [the count of 21 runs](../../raw/trials/2026-10-04-unbounded-criteria-count/method.md) [@trials/2026-10-04-unbounded-criteria-count/method.md]. It reads run records that are not promoted, read-only, on 2026-10-04.

### The audit's severe counts, checked

A simpler command, one `jq` line, reproduces the audit's rounds, severe findings in each round and totals for 17 of its 18 runs. [#135](https://github.com/brindlewick/postmaster/issues/135) differs by one: a coachman's summary of round 5's P2 fixes counts in the audit and not in the command. For [#202](https://github.com/brindlewick/postmaster/issues/202) the command gives the postmaster's 12, 4, 3, 2, 4, 1 and 5 for rounds 1 to 7, the escalation lines give 1 and 2 for rounds 8 and 9, and the 51 gating findings of rounds 1 to 7 are the same. Of those 51, 29 sit in the code that reads shell command text by my reading, 25 to 29 depending on four boundary findings; the postmaster's 28 is inside that range. A run with no finding lines reads zero through the same command, which is the negative control [@trials/2026-10-04-unbounded-criteria-count/results/controls.md].

**One control failed.** For [#124](https://github.com/brindlewick/postmaster/issues/124) the finding lines name no round from 5 to 18 and sum to 28 severe findings. The run's own review checkpoint lists 94, and its escalation line for each of those rounds agrees with the checkpoint's count. [#109](https://github.com/brindlewick/postmaster/issues/109) has no finding lines for rounds 7 and 11, about 7 severe findings by its checkpoint. So a count made from `finding` lines is a floor, the lane audit's table of severe findings by round reads low for these two runs, and its total of 264 is low by about 70. Where the coachman logged a round's findings in an escalation file and not on finding lines, the count does not see them.

### The three cases the rules came from

- **[#202](https://github.com/brindlewick/postmaster/issues/202)**: nine rounds; severe findings per round 12, 4, 3, 2, 4, 1, 5, 1, 2. Criterion 5 asked for "every place outside a lane's folder that the lane read or wrote", from the lane's own record. 19 of the 31 severe findings of rounds 1 to 7 are in the code that reads command text. ### Did the tickets ask for something unbounded?

Each ticket as the workhorses first received it, from the tracker's edit history (for three runs, from the run's own copy), was labelled `yes`, `partly` or `no` against the four shapes by this session and by two readers who saw only the 21 texts in a shuffled order, with the rubric. One of them listed the readers' folder once before reading its brief's restriction; the controls say what it showed. A `yes` means a criterion matches a shape and the ticket names no bounded form for it; `partly` that it matches by what it says and the ticket also names a closed set, an observable, named cases or named formats; `no` that no criterion matches.

- **Agreement.** The two readers gave the same label on 18 of 21 tickets (kappa 0.72) and the same answer to flagged or not on 19 of 21 (kappa 0.81). This session, which had seen outcomes, flagged 10 where the readers flagged 8 and 10, and used `yes` where the readers said `partly`: the same label on 13 of 21 (kappa 0.35 and 0.38), the same flagged-or-not on 17 of 21 (kappa 0.61 and 0.62). By the readers, a ticket is rarely `yes`: one `yes` between them.
- **Controls.** The three tickets the rules were written from, [#202](https://github.com/brindlewick/postmaster/issues/202), [#216](https://github.com/brindlewick/postmaster/issues/216) and [#252](https://github.com/brindlewick/postmaster/issues/252), were flagged by all three. Three tickets that ask for a measurement or a named check, [#158](https://github.com/brindlewick/postmaster/issues/158), [#159](https://github.com/brindlewick/postmaster/issues/159) and [#160](https://github.com/brindlewick/postmaster/issues/160), were `no` for all three. The first is not a test, since the rules came from those cases; the other 18 runs are out of sample.
- **Consensus.** Flagged by at least two of the three: 9 runs, [#109](https://github.com/brindlewick/postmaster/issues/109), [#110](https://github.com/brindlewick/postmaster/issues/110), [#135](https://github.com/brindlewick/postmaster/issues/135), [#163](https://github.com/brindlewick/postmaster/issues/163), [#165](https://github.com/brindlewick/postmaster/issues/165), [#200](https://github.com/brindlewick/postmaster/issues/200), [#202](https://github.com/brindlewick/postmaster/issues/202), [#216](https://github.com/brindlewick/postmaster/issues/216) and [#252](https://github.com/brindlewick/postmaster/issues/252).

Taking the consensus, the flagged runs ran more rounds and had more severe findings:

| | Flagged (9) | Not flagged (12) |
| --- | --- | --- |
| Rounds, median (range) | 5 (3 to 13) | 3 (2 to 20) |
| Severe findings, median (range) | 14 (7 to 68) | 3.5 (1 to 30) |
| In round 1 | 6 | 2.5 |

An exact one-sided rank test gives p = 0.08 for the rounds and 0.016 for the severe findings; with [#124](https://github.com/brindlewick/postmaster/issues/124) and [#109](https://github.com/brindlewick/postmaster/issues/109) read from their checkpoints, 0.08 and 0.028. By finding lines, this session's labels alone give 0.03 for the rounds and 0.015 for the severe findings, reader 1's 0.12 and 0.03, and reader 2's 0.22 and 0.05 [@trials/2026-10-04-unbounded-criteria-count/results/labels.md]. This is a rough guide and not a test. The labels are judgements, the flagged runs already had more severe findings in round 1 (6 against 2.5), which suggests larger or harder changes, the runs span different versions of the flow, a run's rounds past the third are the user's decision, and 21 runs cannot separate the shape from the size of the ticket. The lane audit's arithmetic puts the sample for seeing a two-round difference at about 93 tickets in each group [@trials/2026-10-03-lane-audit/results/numbers.md].

**What a ticket that did not ask for the unbounded looks like.** In the same count, 8 of the 12 unflagged tickets ended within the cap of three rounds, with 1 to 5 severe findings and at most 3 in round 1: a measurement from git ([#158](https://github.com/brindlewick/postmaster/issues/158)), hidden tests per lane branch ([#159](https://github.com/brindlewick/postmaster/issues/159)), a record of what each harness reports ([#160](https://github.com/brindlewick/postmaster/issues/160)), a probe for named platforms ([#201](https://github.com/brindlewick/postmaster/issues/201)), a table of efforts ([#182](https://github.com/brindlewick/postmaster/issues/182)), a refusal where a named directory or branch exists ([#75](https://github.com/brindlewick/postmaster/issues/75)). The four that ran past three rounds were [#57](https://github.com/brindlewick/postmaster/issues/57), [#122](https://github.com/brindlewick/postmaster/issues/122), [#124](https://github.com/brindlewick/postmaster/issues/124) and [#179](https://github.com/brindlewick/postmaster/issues/179): `no` for all three readers on [#57](https://github.com/brindlewick/postmaster/issues/57), [#122](https://github.com/brindlewick/postmaster/issues/122) and [#179](https://github.com/brindlewick/postmaster/issues/179), and for two of the three on [#124](https://github.com/brindlewick/postmaster/issues/124). Their late findings, tagged from their logged text, sit in the states a launch is left in and the records of its attempts ([#57](https://github.com/brindlewick/postmaster/issues/57), 4 of 5 in M4), a matcher for provider text that missed natural phrasings ([#122](https://github.com/brindlewick/postmaster/issues/122), 15 of 18 in M1), the landing steps of the review leg ([#124](https://github.com/brindlewick/postmaster/issues/124), 5 of 5 in M4) and a parser that had to agree with another ([#179](https://github.com/brindlewick/postmaster/issues/179), 1 of 2 in M2). My reading is that the words of these tickets did not flag the mechanism, so a reading by wording alone misses it, and the next section shows where late findings sit.

### Where the late findings sat

The 99 severe findings of rounds 4 and later that have a logged text were tagged from that text alone, in a shuffled list, by this session and two readers: M1 reads or classifies an input it could not list in advance, M2 differs from another implementation of the same decision, M3 forecasts what a command will do, M4 is a state, ordering or concurrency case, M5 is anything else. The three agree on 82 of 99 and at least two on all 99 (kappa 0.84 to 0.87). By majority: M1 32, M2 27, M3 8, M4 18, M5 14. So 67 of the 99, 68%, are in a mechanism of one of the four shapes (shapes 4, 3 and 2, with M1 also covering the open "every"); 18 are in state and ordering, which the four shapes do not name; and 14 are plain defects [@trials/2026-10-04-unbounded-criteria-count/results/tail-findings.md].

Three runs supply 70 of the 99: [#109](https://github.com/brindlewick/postmaster/issues/109) (a port, 25 of its 37 in M2, differences from the bash it replaced), [#122](https://github.com/brindlewick/postmaster/issues/122) (15 of 18 in M1, the provider-text matcher) and [#202](https://github.com/brindlewick/postmaster/issues/202) (8 of 15 in M3, forecasts of what a command will do). [#124](https://github.com/brindlewick/postmaster/issues/124)'s 67 late findings have no logged text and could not be tagged.

The control is round 1 of the same nine runs. Its 92 severe findings, tagged by this session and one reader, are 38% to 42% in M1 to M3 and about 40% in M5, against 68% and 14% in the late rounds. So what is left after the early rounds is mostly in the shapes' mechanisms. Whatever a ticket asked for, the defects that survive early rounds are the ones that are hard to list, so this is consistent with the shapes being where loops fail to converge, and is not evidence for the rules by itself.

### What the user did mid-run

In five of the 21 runs the user bounded a criterion after the lanes had started, and each change is one of the four bounded forms: [#163](https://github.com/brindlewick/postmaster/issues/163) to a list of whole files, [#109](https://github.com/brindlewick/postmaster/issues/109) to behaviour the flow can observe, [#124](https://github.com/brindlewick/postmaster/issues/124) to ancestry and not content, [#202](https://github.com/brindlewick/postmaster/issues/202) to observed changes, [#252](https://github.com/brindlewick/postmaster/issues/252) to a best-effort preview. In the four that had reported, the next round had fewer severe findings. Each change followed a round with several, so a smaller round after it is also what a run that is settling down shows. The table is [the mid-run changes](../../raw/trials/2026-10-04-unbounded-criteria-count/results/mid-run-changes.md) [@trials/2026-10-04-unbounded-criteria-count/results/mid-run-changes.md].

### How sure

- **The counts of rounds and severe findings**: sure of what the finding lines say, with controls and a second record for three runs; they are a floor, and the audit's table is low for two runs.
- **The labels**: moderately sure that a ticket is flagged or not (17 to 19 of 21 agree), unsure of `yes` against `partly`. A label from the words misses what the mechanism forces.
- **That flagged tickets run longer**: suggestive. Possibly confounded by size or difficulty, version and the user's rulings, and 21 runs.
- **That late findings sit in the shapes' mechanisms**: the late tags agree well (kappa 0.84 to 0.87), the round-1 control less (0.54), and the mix changes with the rounds. It rests on three runs and leaves out [#124](https://github.com/brindlewick/postmaster/issues/124)'s late findings.
- **That bounding a criterion shortens the loop**: five runs, each after a heavy round, not separable from settling down.

## What #291 already did

[#291, A ticket's acceptance criteria ask only for what a run can finish](https://github.com/brindlewick/postmaster/issues/291) merged on 2026-10-04 as [pull request 292](https://github.com/brindlewick/postmaster/pull/292), a docs-only change of two files. Read at `origin/main` 905efef, it changed [the template](https://github.com/brindlewick/postmaster/blob/905efef/skills/clerk/ticket-template.md) and [the clerk's instructions](https://github.com/brindlewick/postmaster/blob/905efef/skills/clerk/clerk.md) and did three things, all in prose:

1. **The template gained "A criterion must be finishable"**, under what each part is for. It says the run must be able to show a criterion met in a finite amount of work, and that no tool can decide in general what an arbitrary command or program will do. It lists the four shapes and a bounded form for each: name the closed set and report anything outside it as unknown and fail safe; ask for what the check can observe afterwards; name the cases that must agree and say that any other may differ; name the supported formats and report every other as unsupported.
2. **The Direction section now says whether a check or a guard protects against accident or against a hostile lane**, so a defect that needs hostile behaviour is not a defect of a check that guards against accident.
3. **The clerk's instructions now say to check each criterion against the four shapes and rewrite it in its bounded form before the user sees the draft**, and, if the whole point of a ticket is one of the shapes, to say so in plain words and propose the bounded form.

What it did not do. No script judges any of it: [scripts/ticket-check.ts](https://github.com/brindlewick/postmaster/blob/905efef/scripts/ticket-check.ts) and [scripts/ticket-parts.ts](https://github.com/brindlewick/postmaster/blob/905efef/scripts/ticket-parts.ts) do not look for the shapes, and the rules appear nowhere else in the repository. It does not say which way "unknown" fails or what a large unknown bucket costs, it names no sample form for "every", it does not ask for a number in a criterion to be measured, and it reads the shapes off what a criterion says and not off what the mechanism behind it must do. It does not say what a ticket's size should be.

What the reading says about its wording is under [the four shapes](#the-four-shapes-one-at-a-time) and [the proposals](#proposed-changes). In short, its four shapes and their bounded forms have older names and some support, and nothing read says any is wrong.

## What would settle it

The page stays **claimed**: outside work moves no standing, and the count of 21 runs promotes none of them.

- **The count's question.** Whether tickets flagged for a shape take more rounds. In 21 runs that is suggestive and not a test, since the flagged runs already had more severe findings in round 1, which suggests larger or harder changes. The lane audit's own arithmetic says that to see a two-round difference in mean rounds with the spread of its 18 runs would take about 93 tickets in each group, or 8 if only runs of six rounds or fewer count; a one-round difference takes 372 or 29 [@trials/2026-10-03-lane-audit/results/numbers.md]. So the test has to be prospective and cheap per ticket: P12 records which criteria the clerk rewrote and for which shape, and each `finding` line would also carry a mechanism tag, M1 to M5 as in the count (option C of [when a review loop should stop](review-convergence.md) proposes a file and section on each line, not a mechanism tag). At those rates the comparison can be made without hindsight after 8 to 93 tickets in each group for a two-round difference, depending on whether long runs count.
- **A paired test.** The same ticket written once with an unbounded criterion and once with its bounded form, each run through the flow, compared by rounds and late severe findings. Costly, and the only design that separates the shape from the size of the ticket.
- **The five mid-run rulings** are a cheap natural experiment already running: each future ruling that bounds a criterion can be recorded with the severe findings of the rounds before and after it.
- **A different kind of evidence.** A controlled study of ticket wording on a coding agent's outcome would settle most of this. None was found. The nearest are the benchmark studies in the map.
- **Reading what could not be read.** IEEE 830 and 29148 in their own words, a textbook statement of Rice's theorem, OpenAI's two pages, and the Google paper would firm up five statements here. The studies found and not fetched might add measured evidence on bounded checking and on agents that build to a check they can see.
