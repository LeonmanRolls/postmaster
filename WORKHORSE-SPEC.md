# Workhorse spec: 217 Postmaster's flow runs on macOS, shown by a fixture run on a Mac

## Problem / feature

Postmaster has to run on a Mac as well as on Linux, and today its flow breaks on a Mac. A report from a Mac found the main cause: to tell whether a launch is still running, postmaster reads process details that only Linux has. On a Mac every launch looks finished the moment it starts: the run counts it done within seconds, its Herdr pane closes before the agent writes anything, and the run collects empty output.

A review of the code then found seven more things that break on a Mac. The pane showing a launch's output stops early. Stopping or closing a run's launches misses the ones still running. A second start of a run's step can take over the first. Measuring how much of the merged work came from each lane fails with Apple's git. Scoring a fixture run asks for jq, a tool it never uses. Some of the coachman's shell steps misbehave in zsh, a Mac's default shell. And a launch in a pane falls back to running out of sight when the pane cannot find Bun. Nothing caught these, because every test and every run happens on Linux.

Done: all eight are fixed, and each fix has a test. The tests run on Linux, where postmaster takes its Mac path but Linux's tools and stand-ins play the Mac's, so they cannot show that the Mac's own tools behave as assumed. A fixture run on a Mac that scores clean is what shows it works there. This is the first of four tickets toward full Mac support (D1).

## Acceptance criteria

1. On a Mac as on Linux, postmaster can tell whether a process is still running and when it started; one that has exited but not been cleaned up has ended.
2. The run marks a launch done only once its own process has ended.
3. A background launch that is running is never rejected as one that did not start, while one that really did not start still is.
4. A launch's Herdr pane or tmux window stays open, showing it running as on Linux today, until the launch is done.
5. The pane showing a launch's output keeps showing it until the launch ends.
6. Stopping a run's launches ends everything they started that still runs, as on Linux today.
7. Closing a run's panes or windows leaves open any whose launch still has something running, as on Linux today.
8. A second attempt at a run's step is refused while the first is still running, however it is started and whatever language and date format the machine uses.
9. The run's status shows a running step as still running, not as one that needs attention, whatever language and date format the machine uses.
10. Measuring how much of the merged work came from each lane gives the same result with the git Apple ships as with a current git.
11. Scoring a fixture run needs Node and npm but not jq, as the readme's requirements say.
12. The score's first line, not a check, names the system (Darwin or Linux), its release and processor type as the system reports them, and the Bun and git versions.
13. Nothing in the score names the machine, the user or their home folder.
14. Every shell block in the coachman's instructions does the same in zsh as in bash.
15. A launch placed in a Herdr pane or tmux window runs there, shows its output and finishes as usual, even when the pane's shell cannot find Bun.
16. A fixture run on a Mac, of any fixture ticket and with whatever session host and agents the Mac has, scores clean with every check passing.
17. That run's whole score, unedited, and the postmaster commit it used are posted on this ticket as a comment.

## Decisions

- **D1 (given by the user)** The original ticket becomes four, done in order: this one, then postmaster's own tests passing on a Mac in every pull request, then what only works worse on a Mac, then a check that refuses new Linux-only code. Why: the whole is about three times what one review can take. Instead of: one ticket, too long to review well.
- **D2 (given by the user)** The three new tickets are filed, each carrying the original ticket's words for its part, and each is brought to ready in its own session. Why: rewriting this ticket would otherwise lose those words. Instead of: filing them later from memory.
- **D3 (proposed)** Tests make postmaster check processes the Mac way on Linux through one environment setting that everything a run starts inherits, and real runs, fixture runs included, never set it. Why: there is no Mac where the tests run. Instead of: a setting that makes postmaster act as a Mac in every way, which changes more than the process checks.
- **D4 (proposed)** The measurement uses what Apple's git already offers. Why: only one step needs a newer git. Instead of: requiring a newer git, a new requirement for one step.
- **D5 (given by the user)** Tools a Mac can install are enough, so fixture runs keep needing Node and npm. Why: no Mac comes with nothing installed. Instead of: making fixture runs work with only what a new Mac has.
- **D6 (given by the user)** The fixture score names the system it ran on. Why: the Mac run's output has to show it ran on a Mac. Instead of: a score that does not say where it ran, as today.
- **D7 (proposed)** Wherever postmaster starts Bun itself, it uses the Bun already running, by its path. Why: a launch started in a pane that cannot find Bun would fail the next time it starts Bun. Instead of: adding Bun to the pane's search path, which changes the agent's environment.
- **D8 (proposed)** Each fix comes with a test that fails without the fix and passes with it. Why: a test that never failed proves nothing about the fix. Instead of: tests written to pass on the finished code alone.
- **D9 (proposed)** Where a fix's test cannot fail on Linux, a test that fails whenever anything outside the shared way checks a process stands in for it. Why: the old process checks never take the Mac way, so on Linux their tests pass anyway. Instead of: running the new tests on the old code, where those pass.
- **D10 (proposed)** The merge does not wait for the Mac run, and this ticket stays open until the Mac score is posted. Why: waiting would stall three tickets on one person's time. Instead of: holding the merge for the Mac run.
- **D11 (proposed)** The person who reported the bug is asked to do the Mac run. Why: they have a Mac and saw the failure. Instead of: waiting until someone else with a Mac is found.
- **D12 (given by the user)** This ticket adds no CI job on a Mac; #258 does. Why: the job belongs with the ticket that makes the whole test suite pass on a Mac. Instead of: a small Mac job here for this ticket's own tests, which would check the Mac path on a real Mac before the merge.

## Out of scope

- Counting a launch whose output holds nothing from its agent as unfinished: a separate proposal.
- New protection against a process number being reused, or against a time-zone change while a step runs.
- Commands written inline in the coachman's text, and the other runbooks' shell steps: #260's check covers them.
- Running the coachman's shell blocks under the old bash 3.2 a Mac ships: #258's Mac job does.
- Postmaster's scripts started through their wrappers, which find Bun on the caller's path, and the settings that Bun programs started by postmaster miss today: [#218, Every script runs as its TypeScript file, with no .sh wrapper left](https://github.com/brindlewick/postmaster/issues/218).

## Direction

Linux and macOS, in the language and runtime of the project's other scripts. Processes are checked one shared way, not fixed at each place, and nothing that uses it gets a branch of its own for the Mac. A run already going when this lands keeps working: what it recorded about its launches and locks is read as before. A test that uses the Mac way on Linux says so, never that it ran on a Mac. Where zsh is not installed, the comparison with zsh is skipped rather than failed. It changes the coachman's steps, so it lands only after a fixture run from its branch scores clean. The archived trial scripts and old ticket oracles are not edited. #218 changes the same scripts at the same time; whichever lands second converts the other's.

### Technical notes

- One module under `scripts/lib/` owns every read of `/proc/<pid>/stat` and every listing of `/proc`: [`procStat()` and its callers](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/host.ts#L529-L585), [`processTable()`](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/host.ts#L2671-L2716), [`legStartOf()` and `legSelfStart()`](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/host.ts#L3353-L3391), the lock check in `runs-status.ts`, `alive()` in `view-stream.ts`, and the self-test's reads ([`host-self-test.ts`](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/host-self-test.ts#L1543-L1593) L1545-L1546, L1584, and L4315). It answers live, zombie or absent, and start times: `process.kill(pid, 0)` first (`ESRCH` is absent), then `<root>/<pid>/stat`, or `ps -o stat= -p <pid>` (and the `lstart` and `-A` forms already in use) under `LC_ALL=C` where `<root>` does not exist. A zombie counts as ended, so a lock whose owner is a zombie no longer blocks a start. The bare liveness probes at local.ts L248, host.ts L1643 and L3437, run-meta.ts L219 and inside `alive()` go through it too, and so does [`commandLine()`](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/host.ts#L2720-L2731). Test helpers that read the same facts themselves, such as `runs-status.test.ts` L73 and the self-test's, use the module too, or they fail when forced. Boot id, uptime and a script's own raw arguments (`/proc/self/cmdline`) stay where they are, for #259. (C1, C2, C3, C4, C5, D3, D9)
- Start times keep their present form, the field-19 tick count from `/proc` and the five-word `lstart` from `ps`, so registry records and leg locks written before the change still match. (C6, C7, C8, C9)
- The setting is `POSTMASTER_PROC_ROOT`, read from the environment: unset or empty is `/proc`. A pane's own runner, follower and watchers start in the pane server's environment, not the caller's, so the setting is passed on to them as the caller's environment is to the launch. Where Linux cannot answer as a Mac does, a test puts a stand-in on PATH, as in C8 and C10; production code reads no other platform setting. (C1, C8, C10, D3)
- The report's first five controls are C2 to C4. Its sixth, an empty stream never counting as finished, is out of scope. (C2, C3, C4)
- A registry `member <pid> <start>` line splits at the first space only. `close` and `close-run` wait on the same registry scan ([L5405-L5425](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/host.ts#L5405-L5425)) and close a pane they read as idle. (C6, C7)
- `--source` came in git 2.40. A temporary index (`GIT_INDEX_FILE=<tmp> git read-tree <commit>`) and `check-attr --cached` give the same answer on older git. (C10, D4)
- `fixture.sh score` keeps `npm`, which runs the fixture app's discovered gate, `npm run check` ([`checkGate()`](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/fixture.ts#L534-L565)), and drops `jq`, used nowhere else. The platform line is read from the running system (`os.type()`, `os.release()`, `os.machine()`, `Bun.version`, and the number from `git --version`) and printed by `score` alone, after its input checks and before [`report()`](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/fixture.ts#L761-L770)'s lines; `fixture.test.ts`'s `expectScore` counts eight lines and must allow it. The [README's requirements](https://github.com/brindlewick/postmaster/blob/ede70e2/README.md#L177-L178) name Node and npm for the fixture flow instead of jq. (C11, C12, C13, D5, D6)
- No other runbook's shell block gives a variable several words. Arrays work in bash 3.2 and zsh. Run `scripts/skill-refs.sh` after editing `coachman.md`. (C14)
- Bun is also started by name at host.ts L1987, L2255 (the follower), L4417, launch.ts L1640, stage.ts L57 and fixture.ts L341, L365, L551, and found on PATH at run-meta.ts L572. Each start uses `process.execPath`, every other argument unchanged. A target project's own `bun`, as at verify-library.ts L189, is the project's and stays. The `.sh` wrappers stay: a launch runs with its caller's environment, handed over through the pane's FIFO, and that has Bun on PATH. The Herdr stub's `pane run` ([host-self-test.ts L329-L357](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/host-self-test.ts#L329-L357)) gives the pane the stub's own PATH. (C15, D7)
- Each new test is run once with its fix alone reverted. On Linux C2 to C5 cannot fail that way, so C1's containment test is their failing test; without zsh, C14's unquoted-expansion half is its own. (C2, C3, C4, C5, C14, D8, D9)
- `coachman.md` and `fixture.ts` are in [`docs/coachman-contract.toml`](https://github.com/brindlewick/postmaster/blob/ede70e2/docs/coachman-contract.toml), which names `host.sh`, not `host.ts`. The pull request names #217 with no closing keyword. (C14, C16, C17, D10, D11)
