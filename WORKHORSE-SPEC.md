# Workhorse spec: 252 Cleaning up after a run is one script, with a dry run and clear errors

## Problem / feature

After a run lands, the postmaster cleans up by hand: about ten commands, a little different each time. It checks the style sort, saves what is left in each of the run's working folders, closes the folder's windows, removes the folder and logs it, posts a closing comment, and marks the run done. On 2026-10-03 three of these steps failed without saying what to do next: closing a run's windows stopped without a word ([#227, Teardown closes a run's spaces when its logs hold review findings lists](https://github.com/brindlewick/postmaster/issues/227)), git refused three folders until a person judged their leftovers, and a safety check refused a typed command. Two things are missed every time: nothing removes the scratch folders the coachman makes for the blind tests, and the run's pinned copy of the tool is never released.

Done: the postmaster writes what needs judgment, the style sort and its closing words, then runs one command, first as a dry run. The command saves what is left in each folder before removing it, flags any work that never landed for a person, logs every action, and ends with a summary a script can read.

## Acceptance criteria

1. One command takes a landed run to done, in place of the hand steps.
2. The command changes nothing on a run that is not ready: not yet marked shipped, its last leg still running, or its style findings not sorted.
3. A dry run shows every action the command would take, in order, and changes nothing.
4. The command cleans every working folder the run made, the blind-test scratch folders included, and no other folder.
5. Before a folder is removed, its uncommitted changes, its untracked files and any commits no branch holds are saved with the run's records.
6. The summary flags each removed folder whose saved changes hold work that no branch's commits have.
7. A folder is removed only after its windows are closed.
8. The run's preview server is stopped if it still runs.
9. The postmaster's closing words, a line for the run log and the ticket's closing comment, each go to their place once.
10. The closing steps, the closing words and the done mark, wait until all the run's folders are gone.
11. Once the run is done, its pinned copy of the tool is released, unless another run still uses it.
12. Whatever the command cannot do, it names with the step and what to do next; nothing ends silently.
13. Every action the command takes is logged as it happens.
14. Run again after a stop, the command carries on and repeats no step already done.
15. The command can print its summary as one record a script can read.
16. The postmaster's after-merge instructions call the command in place of the hand steps.
17. A fixture run from the change's branch scores clean.

## Decisions

- **D1 (given by the user)** Cleaning up after a run is one script, with a dry run, errors that say what to do next, and a summary a script can read. Why: an agent uses a script well, and works prose out afresh each time. Instead of: the hand steps in the postmaster's instructions.
- **D2 (proposed)** The command does every step after the landing that needs no judgment: the preview, the folders and every window the run opened, the ticket's done state, the closing words, the done mark and the release. Why: each follows from the run's records. Instead of: keeping the ticket's state and the release by hand.
- **D3 (proposed)** Before the command runs, the postmaster writes the style sort and the closing words; after it, the postmaster puts tool faults, style proposals and any flagged folder to the user and archives finished threads. Why: these need reading, not a rule. Instead of: a closing comment the command writes from the records alone.
- **D4 (proposed)** The command takes the shipped mark as proof of the landing, and nobody confirms the merge by hand any more. Why: the postmaster sets that mark only after its landing check has confirmed the merge. Instead of: confirming it again, which needs the provider's report of a pull request.
- **D5 (proposed)** A run's folders are those its records name, plus any folder in the project's worktree folder named for the ticket and a dash, even one a person made; the coachman will name its blind-test scratch folders so. Why: the flow names its other folders so. Instead of: a new record of each scratch folder.
- **D6 (proposed)** Files git ignores are not saved and go with their folder, as today: installed packages, build output, and the lanes' copies of their evidence. Why: the first two are rebuilt, and the evidence was read when the lanes were judged. Instead of: saving the evidence too, a small addition if it is wanted later.
- **D7 (given by the user)** Every run folder is removed once saved; one whose saved changes hold work no branch's commits have is flagged in the summary, untracked files aside. Why: the save keeps a copy, and the flag still brings work that never landed to a person. Instead of: keeping such a folder until a person has looked, which needs a rule and a way to name it for removal.
- **D8 (proposed)** A fixture run is cleaned like any other. Closing the fixture project's own window, and the score, stay with the supervising postmaster. Why: the fixture's own postmaster runs the command inside that window, and the score must come from the change's branch. Instead of: a fixture mode in the command.
- **D9 (proposed)** The dry run makes the real run's checks, prints its plan, flags included, and ends with the real run's exit status, writing nothing, its log included. Why: it shows what will happen. Instead of: a dry run that lists steps without checking them.
- **D10 (proposed)** The summary gives the run, whether it was a dry run, the outcome, each step and folder with what happened, where each save went, which folders are flagged, and after a stop what to do next: as plain lines, or as one record on request. Why: a person reads lines, the postmaster a record. Instead of: the record only.
- **D11 (proposed)** The command ends one of four ways, each with its own exit status: done; stopped partway, as on a folder still in use; not ready, with nothing changed; or a fault in its call. Why: each needs its own next step. Instead of: one status for all failures.
- **D12 (proposed)** A folder the command cannot clean is named and left in place, and the rest are cleaned; a failing closing step stops the command there. Why: one stuck folder should not hold up the rest. Instead of: stopping at the first folder that fails.
- **D13 (proposed)** A fault in the command stops the cleanup and goes to the user, as a fault in the flow's checks does; the postmaster does not redo its steps by hand. Why: it removes folders, and a fault there could lose work it should have saved. Instead of: working around a fault by hand, which brings back the judgment calls.
- **D14 (proposed)** [#227](https://github.com/brindlewick/postmaster/issues/227) goes first, and this ticket builds on its fix. Why: the command closes windows through the step 227 repairs, which stops without a word on every run with a bug review, and 227 is small, signed off and needs no fixture run. Instead of: folding 227 in, or working around it here.

## Out of scope

- Abandoning a run, and runs from before the two-leg contract: the command refuses them, and their own steps stay.
- Blind-test scratch folders of runs dispatched before this change, when they are not named for the ticket.
- Closing a fixture project's own window, and scoring (D8).
- Ticket steps for a tracker the flow has no adapter for: they stay with the postmaster.
- Stopping tests from leaving files in a lane's folder.
- Teaching the fixture score to check the cleanup.
- Checking the other scripts against the same rules.

## Direction

Linux and macOS 13 or newer, in the project's script language and runtime, with tests beside it and a positive and a negative control for each count. It changes the postmaster's after-merge steps and the coachman's naming of its blind-test folders, and adds the command to the coachman contract's file list, so it merges only after a fixture run from its final head scores clean. These stay as they are: the run's branches are kept, its records are never deleted, nothing that runs is stopped but the preview, and the command runs from the live copy of the tool, not the run's pinned copy. It waits for [#227](https://github.com/brindlewick/postmaster/issues/227) (D14).

### Technical notes

- The command is `scripts/aftercare.ts` alone, with no `.sh` wrapper, run as `bun --no-env-file --config=/dev/null <tool>/scripts/aftercare.ts <dispatch>`, the form `coachman.md` already uses for `summary-evidence.ts`, taking `--dry-run`, `--json`, `--comment <text>` and `--run-log <text>`. It runs from the live checkout, `<tool>`, never the run's pin `<rt>`, as [Legacy Stage G already says of teardown](https://github.com/brindlewick/postmaster/blob/40d50ce/skills/postmaster/postmaster.md#L698-L707). (C1, C3, C9, C15, D1)
- Ready means: the manifest's stage is `shipped`, or `done` on a rerun; `.leg-<n>-exited` exists for the manifest's `leg`; and [`style-findings.sh check`](https://github.com/brindlewick/postmaster/blob/40d50ce/scripts/style-findings.ts#L1-L15) exits 0, its exit 2 being not ready and its exit 1 a fault. A run without `coachman_contract: 2` ([`isCurrent`](https://github.com/brindlewick/postmaster/blob/40d50ce/scripts/stage.ts#L116-L135)), or at `abandoned`, is a fault in the call, and the message names the steps that serve it (Legacy Stage G, or abandoning); a fault in the call wins over not ready. A leg with no exit marker whose process is gone is a spent run, not ready, and the message points to Stage D. A refusal writes no log line. (C2, C12, D11)
- `shipped` is set only by the postmaster, once `landing.sh already-landed` says `landed` or the user has said there is nothing to land ([postmaster.md L565-L630](https://github.com/brindlewick/postmaster/blob/40d50ce/skills/postmaster/postmaster.md#L565-L630)); the command asks git nothing about the merge, and Stage G's step 1 confirmation goes. (C2, C16, D4)
- The run's folders: [`runWorktreePaths`](https://github.com/brindlewick/postmaster/blob/40d50ce/scripts/host.ts#L5479-L5596) gives the synthesis, workhorse and reviewer folders from the records; add every entry of `<repo>/.worktrees` named `<TICKET>-` and more, `<TICKET>` as that function derives it. Nothing outside `<repo>/.worktrees` is touched: not the pins under `POSTMASTER_TOOL_PINS`, and not a checkout of the tool a reviewer made elsewhere. [`cut-scratch.sh --kind`](https://github.com/brindlewick/postmaster/blob/40d50ce/scripts/cut-scratch.ts#L1-L37) tells a detached worktree from a clone, and `--remove` removes either; a folder on a branch is removed with `git worktree remove --force` after its save, from outside it. An entry that is neither a worktree nor a clone of the repository, a locked worktree, and the caller's own working directory are left in place and named. (C4, D5, D12)
- A folder left in place, in use or not a git folder, gets a `note` naming why, and the rest are still cleaned; it goes on a later run once that cause is gone. On a rerun every folder left is judged again, and one whose save would be unchanged is not saved again. (C12, C13, C14, D12)
- The blind-test scratch is cut at harvest, [coachman.md L460](https://github.com/brindlewick/postmaster/blob/40d50ce/skills/postmaster/coachman.md#L454-L462), with no name given; name it `<repo>/.worktrees/<TICKET>-oracle-<lane>` there and in the [table of where things live](https://github.com/brindlewick/postmaster/blob/40d50ce/skills/postmaster/coachman.md#L23-L48). (C4, D5)
- The save goes to `<dispatch>/stray/<folder>.*`, as the runbook already names it: `git status --short`, `git diff --binary`, `git diff --cached --binary`, the untracked files from `git ls-files --others --exclude-standard -z` as a tar, and the commits from `git rev-list HEAD --not --branches` as patches. A part with nothing in it is not written, so nothing is ever removed after it was written; a second save of a folder goes beside the first, which stays. Ignored files, by git's own rules, are not saved; a lane's evidence copy under `.postmaster/verify/` is ignored through `info/exclude` ([verify.ts L495-L501](https://github.com/brindlewick/postmaster/blob/40d50ce/scripts/verify.ts#L495-L501)). (C5, D6)
- A tracked file flags its folder when its content, in the index, the work tree or an unbranched commit, is in no commit a local branch of the project holds, at any path: `git log --branches --find-object=<blob>` names a commit that adds it when one does. A deletion or a change of mode alone never flags a folder; an unmerged path always does. In a clone scratch, judge against the project's branches, never the clone's own, which do not hold the lanes' commits. Untracked files never flag a folder. The flag, with its files, goes in the summary and in that folder's `teardown` detail. (C6, C13, D7)
- Windows: [`host.sh close <folder>`](https://github.com/brindlewick/postmaster/blob/40d50ce/scripts/host.ts#L2927-L2948) for each folder before it is removed, and [`host.sh close-run <dispatch>`](https://github.com/brindlewick/postmaster/blob/40d50ce/scripts/host.ts#L5788-L5834) for the spaces and windows still tagged for the run. `close` refuses while a launch runs in the folder, or when a person has a pane open there; that folder is left in place and named, and the rest go on. `close-run` exits 2 with no message when Herdr cannot list a run space's panes ([L5729-L5733](https://github.com/brindlewick/postmaster/blob/40d50ce/scripts/host.ts#L5729-L5733)), which #227 leaves as it is; the command names the step all the same. The command never calls `host.sh stop` or `stop-run`. (C7, C12, D12, D14)
- The preview's pid file is `<dispatch>/render/preview.pid`, written by `host.sh run --pidfile` ([coachman.md L1080-L1087](https://github.com/brindlewick/postmaster/blob/40d50ce/skills/postmaster/coachman.md#L1080-L1087)). Stop that launch's whole group, and only while the launch registry under `POSTMASTER_HOST_STATE` still records that pid with its start time, so a pid since reused is never signalled; a pid that runs nothing is already stopped, and a preview that outlives its stop leaves the synthesis folder in place. (C8, D2, D12)
- A log line that cannot be written stops the command before its next action, as a fault in a control. A second call on a run while one is running there is a fault in the call, naming the first. Closing words that changed after a part was posted leave that part as posted. (C12, C13, C14, D11, D13)
- The dry run reads what the real run reads, the tracker's state and the launch registry included, writes nothing, and lists the closing steps after a folder it would leave in place as waiting. (C3, D9)
