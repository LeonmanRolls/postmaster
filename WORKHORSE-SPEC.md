# Workhorse spec: 216 The private-data check is TypeScript run by Bun, and flags little of the project's own code

## Problem / feature

Nothing in the flow stops a run from publishing personal data, a secret or private context. [#135, A gate check refuses any change that carries personal data or a secret](https://github.com/brindlewick/postmaster/issues/135) built a check as shell scripts with embedded Python, which cannot land: [#109, Rewrite the scripts in TypeScript, run by Bun](https://github.com/brindlewick/postmaster/issues/109) removed Python from the flow, and the user ruled on 2026-10-02 that no new Python is added. It also flagged far too much of the project's own code. On 2026-10-03 the user settled what it refuses: personal data, secrets and private context, found by patterns alone with no model. [#208, Research: publish the private-data scanner as a library](https://github.com/brindlewick/postmaster/issues/208) measured such patterns for personal data.

Done: everything a run publishes from this project is checked inside the gate, findings are fixed before anything is published, the user hears of each one, and run records copied into the wiki are scrubbed first.

## Acceptance criteria

1. The check is TypeScript run by Bun, like the project's other scripts, and needs no Python.
2. In this project, the gate checks everything a branch adds since main: every line a commit adds, even one deleted later, file names, commit messages, each commit's author and committer, and what a merge adds.
3. It reads every file as a person would see it, so a value hidden in the stored form of a session transcript is still found.
4. It finds secrets as the first version does: private keys by any line of one, access tokens, bearer credentials, and long literal values given to secret-sounding names.
5. It finds personal data with #208's patterns alone, with no model and no network.
6. On #208's two held-out test sets it finds at least as much personal data as #208's second version did, with no more false alarms.
7. It finds private context: home folders with a user's name, private machine names and the addresses ssh uses for them, private network addresses, account, organization and session ids, and lines that credit an assistant or a tool.  private-data:allow private-host -- made-up prose describing the feature
8. This run scans main's whole history once, from its first commit, and finds at most 50 suspects, each judged made-up or real.
9. A finding fails the gate like a lint error, named by its rule and its place.
10. No message a person reads shows a finding's value, even when the value is in a file name.
11. The coachman fixes a finding without asking the user.
12. The user is told of each finding once, marked ones included, as soon as the postmaster next checks the runs.
13. The ship card lists every finding of the run and whether it was removed, marked as made-up, or scrubbed.
14. Made-up data that looks real passes only when a marker beside it names the rule and gives a reason.
15. A marker on a line where its rule finds nothing fails, so no marker outlives the data it was for.
16. Made-up data can be marked only in files: in a commit message or a text the postmaster posts, it must be reworded.
17. A finding left only in an earlier commit is taken out of the branch's history before the branch is pushed, without changing its final files.
18. A finding in a commit already pushed goes to the user, since a pushed branch is never rewritten.
19. Copying a run's records into the wiki replaces each finding in the copy with a placeholder, leaving the run's own records as they were.
20. The copy replaces the encrypted reasoning some model tools store in transcripts with a placeholder.
21. The copy finishes only when it checks clean.
22. The gate fails when a change commits anything from the flow's private folder in the project except the shared project settings file.
23. Every rule is proven by tests that show it finding what it should and passing what it should not, and that fail when it is switched off.
24. The made-up values already in the project's files are rebuilt or marked, so the check finds none.
25. Other scripts that use the first version's check get their answers in the same form.
26. The first version's changes to the status poll, the gate runner, the runbooks and the wiki's instructions are kept, except where a decision changes them.
27. Its memory grows only with the longest line, never with the size of a file.
28. No line stalls it: a line of a megabyte scans within a second, and nothing in a line is skipped.
29. In every project, the postmaster checks each pull request text and ticket comment it posts for a run, and takes out any finding before posting.

## Decisions

- **D1 (proposed)** In this project, the check runs inside the gate. Why: a separate failing check goes to the user, and a finding must not wait on them. Instead of: separate checks, as the first version had.
- **D2 (proposed)** Code that only reads or names a secret, a path, a machine or an id is not a finding, while all real data the first version's tests find is still found. Why: the first version flagged so much ordinary code that the real findings were buried. Instead of: its rules unchanged.
- **D3 (proposed)** An address on a one-word or private network name is a machine address, found as private context rather than as an email. Why: it names a machine, not a person. Instead of: reporting it as an email.
- **D4 (proposed)** The held-out comparison counts personal data only. Why: one test line holds a made-up key, which is not personal data. Instead of: counting it as a false alarm.
- **D5 (proposed)** A malformed marker fails only beside a finding. Why: documentation, this ticket included, shows what a marker looks like. Instead of: failing it everywhere.
- **D6 (proposed)** Commit authors and committers are checked. Why: they are published with the commit. Instead of: skipping them, as the first version did.
- **D7 (proposed)** The verdict on each history suspect stays in this run's private records, and its ship card shows the counts. Why: the card is published with the pull request, and old commits cannot change. Instead of: each suspect on the card.
- **D8 (proposed)** An untold finding comes first in the status poll. Why: the first version could hold a finding back while a question waited. Instead of: its order.
- **D9 (proposed)** The runbook steps go where today's runs read them. Why: the first version put several in stages no new run reaches. Instead of: its steps as written.
- **D10 (proposed)** Encrypted reasoning is removed only when records are copied into the wiki. Why: the gate refuses personal data and secrets only. Instead of: refusing it in every commit.
- **D11 (given by the user)** The first version's self-tests become ordinary tests. Why: the other scripts moved theirs the same way. Instead of: a self-test option.
- **D12 (given by the user)** No secret rule is weakened to meet the limit of 50; made-up secrets in the current files are rebuilt or marked instead. Why: the count must measure the rules. Instead of: loosening them.
- **D13 (given by the user)** No message shows scanned text, errors included. Why: Bun's errors quote what they failed on. Instead of: passing errors through.
- **D14 (given by the user)** Where a rule is unchanged, the new check prints exactly what the first version printed for other scripts, recorded once. Why: other scripts read it. Instead of: comparing by eye.
- **D15 (given by the user)** Names with accented letters are found, and places in a line are counted as before. Why: Bun treats letters differently from Python. Instead of: plain letters only.
- **D16 (given by the user)** The large-file test runs under a 512 MB memory limit, and a crash fails it. Why: Bun cannot start under the first version's 256 MB. Instead of: skipping on a crash.
- **D17 (proposed)** Other projects' gates are unchanged; in them, only the text the postmaster posts is checked. Why: each project owns its gate, while the flow writes that text and posts it in the user's name. Instead of: adding the check to every project's gate.
- **D18 (proposed)** If main's history still shows more than 50 suspects with no rule weakened, the run asks the user. Why: the rules are the user's choice. Instead of: the run loosening a rule on its own.
- **D19 (proposed)** Each finding is told once, however many times the gate sees it. Why: the gate runs many times while a finding is being fixed. Instead of: telling it again after every run.
- **D20 (given by the user)** Private context is refused like personal data. Why: it must not go out, and the earlier ruling that allowed it rested on a misunderstanding. Instead of: allowing it, as ruled on 2026-10-02.

## Out of scope

- Names in prose, such as a first name on its own.
- Rewriting anything already pushed, main's history included.
- Whether a run's workhorse files may land on main; they are checked like any other file.
- Branch and tag names, which the flow makes from ticket numbers and lane names.
- Text hidden in other encodings, such as base64.
- Publishing the check as a library.

## Direction

Linux and macOS, with nothing beyond what the project's other scripts use. #135's branch is the reference for how the check works: read it, never check it out or run it in place. Its script names, command forms, output lines, marker form and exit codes stay, and so do its rules for private context, narrowed so that ordinary code is not flagged. #208's patterns, with their rule names, are the starting point for personal data. It changes the coachman's steps and the status poll, so it lands only after a fixture run from its branch scores clean. The wiki's page checker stays as it is.

### Technical notes

- The first version is local branch `135`, based on 0620bfc and not on GitHub: `scripts/{scrub-check,scrub-rewrite,raw-promote,tree-check,verify-merge}.sh` and `oracle-135.sh`. Read it with `git show 135:<path>`. `scrub-check.sh`'s header documents every form, output line, marker rule, the detections log and the exit codes, which stay. Each new script is a `.ts` with a one-line wrapper of `host.sh`'s form and a `.test.ts` beside it; the gate's `lint/test-beside-target.ts` fails a test without its script. (C1, C25, D11, D14)
- Range scan: `scrub-check.sh <base> <head>` prints `<commit>:<path>:<line>: <rule>`, `(message)` for a message, `(author)` and `(committer)` for the identities, line 0 for a file name; exit 0 clean, 1 findings, 2 usage or unreadable. `<base>` may be git's empty tree, which scans from the root commit. Author and committer are read as a git identity line, so #208's identity and name rules apply. (C2, C8, C9, D6)
- Transcripts: strip CSI and OSC sequences, decode JSON strings and JSON held in them to a stated depth of at least four (the first version uses 64), decode a cut-off last record as far as it goes, and read UTF-16 by its byte-order mark. Every file is read this way; no other encoding is undone. (C3)
- Secrets are the first version's `token` and `dotenv` rules, with its minimum lengths and absence markers, private-key headers and block lines found alone, inside quotes or after `# `, and AWS ids starting `ASIA` as well as `AKIA`. Its rule for a long value under a secret-named field takes [review-findings.ts L789](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/review-findings.ts#L789), [project-settings.ts L281](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/project-settings.ts#L281) and [plane.ts L1052](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/plane.ts#L1052) for secrets, and its `.env` rule the name list at [oracle-102.sh L59](https://github.com/brindlewick/postmaster/blob/ede70e2/oracle-102.sh#L59): a value that is code (a call, a property, an expression) or a list of names is not a secret. (C4, D2)
- Personal data is #208 version 2's [patterns.ts](https://github.com/brindlewick/postmaster/blob/ede70e2/raw/trials/pii-patterns/apparatus/patterns.ts): its rules, exclusions and rule names, plus `token`, `dotenv`, `marker` and `encrypted-reasoning`. The citation exclusion reads the file's front matter at the commit scanned, since a diff has no context. Underscores and hyphens split a field name into words for every word rule. The email shape needs a dot in the domain. Word classes go through [scripts/lib/text.ts](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/lib/text.ts), whose guard test fails a hand-written `\w`, `\d`, `\b` or `\s` ([text.test.ts L104-L107](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/lib/text.test.ts#L104-L107)). (C5, D3, D15)
- The held-out sets are `raw/trials/pii-patterns/results/heldout/lines.json` and `heldout2/lines.json`, each line stored in three-character pieces with a label, scored by #208's `run.ts heldout`, per set and by lines. A line is found when it has a personal-data finding, and raised when a `none` line has one. Set 2's line 17 is a made-up `sk-` key labelled `none`. (C6, D4)
- Private context is the first version's `private-path`, `private-host`, `account-id`, `key` and `assistant-attribution` rules, narrowed. At 0620bfc they gave 908 of its 928 suspects, nearly all code or made-up data: `process.env.HOME` read as a host on a `.home` network, thread, workspace and session ids, `session` and `email` field names, and a test file at `<trial>/home/note.txt` read as a home directory. A path or host built in code, a field name with no value, and a placeholder user or host pass. A machine name is private when it is one word after ssh or scp, or ends in a private network suffix (`.internal`, `.local`, `.lan`, `.home`, a tailnet's `.ts.net`); such an address is `private-host`, never `email`, though #208's email rule finds the last four today. Assistant and vendor co-author trailers and generated-with footers are `assistant-attribution`; a person's name in a co-author line is personal data. The rewrite cuts an assistant's trailer from a message, as the first version's does. Not ported: `wiki-lint.ts`'s page rules and the wiki skill's lines listing them, since the gate scans wiki pages, and `oracle-135.sh` as a file. (C7, C17, C26, D2, D3, D20)  private-data:allow private-host -- made-up prose describing the feature  private-data:allow private-path -- made-up prose describing the feature
- The census is `scrub-check.sh <empty tree> <main>`, `<main>` the main commit the branch last merged, else its base; a suspect is one place (a file line, a message line or an identity), however many rules fire on it. The census is this run's measurement, not a step of every run. Save it in the dispatch folder with counts by rule and a made-up or real verdict per line; the card shows counts by rule and by verdict. Over 50 with no rule weakened, the coachman escalates. (C8, D7, D12, D18)
- The gate: `package.json`'s `check` runs the range scan and `tree-check.sh` against `origin/main` before `tsc`, and `.postmaster/project.toml` takes no `scrub` or `tree` entry. Stage F puts any failing check but the gate to the user ([postmaster.md L506-L508](https://github.com/brindlewick/postmaster/blob/ede70e2/skills/postmaster/postmaster.md#L506-L508)). (C9, C22, D1)

- Detections: with `POSTMASTER_DETECTIONS_LOG` set, each finding but a marker fault is appended as one JSON line with rule, redacted file, line, commit and time, and `"via":"marker"` when a marker hid it; `--pr-description` logs too. `verify.ts` sets the log to `<dispatch>/detections.jsonl` and drops `SCRUB_CHECK_DISABLE` from the gate. `runs-status.ts` shows `TELL` while the log holds a finding `.detections-told` lacks, before every other state, comparing rule, file, line and commit and ignoring the time; `runs-watch.ts` wakes on it; the postmaster tells the user and appends the told lines. (C12, D8, D19)
- Runbooks: keep the first version's hunks in current stages (coachman.md near [L293](https://github.com/brindlewick/postmaster/blob/ede70e2/skills/postmaster/coachman.md#L293), L524, L622 and L753, and `TELL` beside postmaster.md's Stage D list near [L289](https://github.com/brindlewick/postmaster/blob/ede70e2/skills/postmaster/postmaster.md#L289)). The coachman runs the rewrite before it writes the card, and escalates a finding in a pushed commit as Stage E does. Script paths go through `<tool>`; run `scripts/skill-refs.sh` after. (C11, C13, C17, C18, C26, D9)
- Markers: `private-data:allow <rule> -- <reason>` on the line, or `private-data:allow-next-line <rule> -- <reason>` above it, inert in messages and in all text the postmaster posts. A valid marker that hides nothing faults, a stale one after its data was removed included; marker-shaped text with no rule, no reason or an unknown rule faults only beside a finding. A next-line marker inside a string reaches only that string's next line; marker text inside an escape sequence is ignored. (C14, C15, C16, D5)
- `scrub-rewrite.sh <base>` rewrites only unpushed commits, checks `HEAD^{tree}` is unchanged and the rescan is clean, and refuses with exit 2, naming the commit, a finding in a merge, a message or an identity, and any pushed branch. (C17, C18)
- `raw-promote.sh <source> <dest>` writes `<redacted:<rule>>` placeholders and removes a thinking block's `signature`, a `redacted_thinking` block's `data` and any `encrypted_content`, at any decoded depth, keeping each JSON line valid. `tree-check.sh` refuses those in a file added under `raw/`. It rescans the copy, refuses an existing destination with exit 2, and copies nothing on a marker fault, exit 1. (C19, C20, C21, D10)
- `tree-check.sh <base> <head>` fails on anything under `.postmaster/` but `project.toml`, staged or committed in the range, a merge included. (C22)
- Fixtures: positives are assembled from fragments at test time; `SCRUB_CHECK_DISABLE` takes a rule name, `messages`, `merges` or `markers`. The first version's self-test and oracle checks of kept behaviour become tests under their names, counts dropped, and the summary compares counts. (C23, D11)
- Made-up values at the base: #208's patterns flag addresses in `tool-faults.ts`, `tool-faults.test.ts` and `review-page.test.ts`, and the secret shapes take [project-settings.ts L370](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/project-settings.ts#L370), [project-settings.test.ts L270-L278](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/project-settings.test.ts#L270-L278) and [oracle-112.sh L79](https://github.com/brindlewick/postmaster/blob/ede70e2/oracle-112.sh#L79). Rebuild each from fragments or mark it. (C24, D12)
- Goldens: the first version's output and exit codes for `--spans`, `--findings`, `--safe-path` and `--log-detection`, on inputs for the unchanged rules `token`, `dotenv` and `marker`, under `scripts/fixtures/` as [tool-faults-parity.json](https://github.com/brindlewick/postmaster/blob/ede70e2/scripts/fixtures/tool-faults-parity.json) is, with the regeneration command in `_note`. Record them with Python 3 from `git show 135:<path>` exports in a scratch folder. `--spans` offsets count code points, as Python did, over broken UTF-8 and characters outside the Basic Multilingual Plane. (C25, D14, D15)
