# Workhorse spec: 268 A run cannot add a comment that switches off a check without the user's word

## Problem / feature

The gate's checks can be switched off from inside a change. A comment does it for a line or a file: the linter's disable comments, Biome's ignore comments and TypeScript's ignore comments. A line in a check's own settings does it for the whole project. A run that meets a refusal it cannot fix can add one, and the gate then passes. Nothing in the landing looks for them, and where the postmaster holds the merge word, as it does on this project, it can merge one without any person deciding it. [#260, A check refuses new Linux-only constructs in the scripts and runbooks](https://github.com/brindlewick/postmaster/issues/260) makes this sharper: its rule keeps the linter's own switch-off working, by the user's decision, so the only thing between a Linux-only use and main is whether someone sees the comment.

Done: before the postmaster lands a run, a check lists every switch-off the run adds, the ship card shows that list, and the postmaster does not land the run until the user has approved each one. A person can still switch a check off; a run cannot do it silently.

## Acceptance criteria

1. Before a run lands, a check lists every switch-off comment the run adds, with its file, its line, what it switches off and the reason beside it.
2. The check also lists every change the run makes to the settings of the project's checks.
3. Text that only looks like a switch-off, such as a test's input written in a string, is not listed.
4. A switch-off that main already has is not listed, even after main is merged into the run's branch.
5. The ship card shows the list for the run's final commit.
6. A run that adds a switch-off is not landed until the user has approved each one.
7. Each approval is recorded in the project's ledger with the user's words and the switch-off it covers.
8. A switch-off with no reason beside it goes back to the run before the user is asked.
9. A switch-off the user refuses goes back to the run to be removed.
10. A run that adds no switch-off lands as it does today.
11. A fixture run from the branch scores clean.

## Decisions

- **D1 (proposed)** The approval is always the user's, even where the postmaster holds the merge word. Why: the hold is there so that a person decides, and a postmaster that approved its own run's switch-off would be the silent path again. Instead of: letting whoever holds the merge word approve.
- **D2 (proposed)** The user approves by a word to the postmaster, which asks them with the ship card before it opens a pull request or merges. Why: it works the same on both landing routes, and the user already answers the postmaster there. Instead of: approving in the pull request, which a local merge does not have.
- **D3 (proposed)** Each approval is kept in the project's ledger. Why: the ledger is the project's record of what was done and on whose word, and it outlives the run. Instead of: the conversation alone, which nothing reads back.
- **D4 (proposed)** Every switch-off a run adds carries its reason beside it in the code. Why: the reason is what the user judges, and the next reader of the code sees why the check is off there; Biome already obeys none without one. Instead of: the reason only in the user's word, which a reader of the code never sees.
- **D5 (proposed)** The comments counted are TypeScript's, the linter's under both its spellings, and Biome's, for any rule; another tool's are added, one entry each, when a project's gate runs it. Why: these switch off this project's checks and the fixture app's, while the shell-check comments merged so far sat in scripts no gate checks. Instead of: every language's from the start.
- **D6 (proposed)** A change to the linter's, the formatter's or the type check's settings, or to what the gate's command runs, counts like a comment. Why: a rule turned off there is the same bypass one file away, and the linter's settings already turn two rules off for the whole project. Instead of: comments only, which would push a held run there.
- **D7 (proposed)** Removing a switch-off is not listed and needs no word. Why: it turns a check back on, and the gate shows the code passes without it. Instead of: listing removals for the user to see.
- **D8 (proposed)** An approval holds for the same comment over the same code, wherever its line moves; a change to either needs a new word. Why: merging main moves lines without changing what was approved, while a moved comment can cover other code. Instead of: approving a line number, or the whole run.
- **D9 (proposed)** The coachman runs the same check before it writes the ship card; the project's gate is not changed to report them. Why: the gate is each project's own command, and the coachman can still remove what it can fix and give each kept one its reason. Instead of: a step in this project's gate alone.
- **D10 (proposed)** This ticket does not wait for #260, and is best landed before it. Why: #260 lands last of four tickets, and once this is in, any switch-off #260's run adds waits for the user's word. Instead of: landing after #260, which leaves its rule open to a silent switch-off in between.

## Out of scope

- A run writing an approval into the records itself: who wrote a line in the ledger is a claim today, and this ticket adds no proof of it.
- Skipping or deleting a test, or editing a check's own code: the reviewers read these like any other change.
- The checks a project declares for its runs: a run's checks are fixed when it is dispatched, so changing the declaration cannot help it pass.
- The two switch-off comments already on main, which switch nothing off, since the linter's settings turn their rule off for the whole project.
- Merges that are not a run's, such as a pull request a person opens.
- The ledger's own schema, which [#19, Ledger: a validated schema, data in fields, a coverage control and a way to query it](https://github.com/brindlewick/postmaster/issues/19) covers; an approval is one more kind of line in it.

## Direction

TypeScript, on Linux and macOS, with no new dependency. The check works for every project the postmaster lands, not only this one. It changes the landing and the coachman's last step, which are part of the coachman's contract, so it lands only after a fixture run from its branch scores clean. Runs dispatched before it lands are held the same way at landing; only their cards lack the list. It does not wait for #260 (D10).

### Technical notes

- The comment forms. TypeScript: `@ts-ignore`, `@ts-expect-error` and `@ts-nocheck`, in a `//`, `/* */` or `/** */` comment. The linter: `eslint-disable`, `eslint-disable-line` and `eslint-disable-next-line`, and the same spelled `oxlint-`, with or without rule names (none means every rule); a block `eslint-disable` or `oxlint-disable` runs to its `-enable` or the end of the file. Biome: `biome-ignore`, `biome-ignore-all` and `biome-ignore-start` (to `biome-ignore-end`), each `<category>: <reason>`. Files: `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs` anywhere in the tree, `raw/` and `fixtures/` included. A new form or tool is one entry. (C1, C3, D5)
- A reason is the text after ` -- ` in the linter's comments (ESLint's description form, which Oxlint 1.86 obeys), any text after the directive in TypeScript's (a leading `--` or `:` dropped), and the text after the colon in Biome's. Empty or blank text is no reason. (C1, C8, D4)
- What a run adds: compare the ticket head with the merge base of the ticket branch and the default branch, file by file. A switch-off is identified by its file, its comment text and, for a line or next-line form, the trimmed text of the line it covers; the head adds one when it holds more of an identity than the merge base does. The line number is for the listing only. Removing the comment that ends a block (`eslint-enable`, `oxlint-enable`, `biome-ignore-end`) widens the block, so its opening comment counts as added. (C1, C4, D7, D8)
- Only real comments count: read each file with a small scanner that tells comments from strings, template literals (with `${}` nesting) and regex literals. Runtime imports stay Bun's built-ins and Node's standard modules ([AGENTS.md L231-L234](https://github.com/brindlewick/postmaster/blob/8157c7a/AGENTS.md#L231-L234)), so no TypeScript or Oxlint parser at run time, and nothing that works on Linux alone. (C1, C3)
- The settings files, anywhere in the tree, added, changed or deleted: `tsconfig*.json`, `jsconfig*.json`, `.oxlintrc.json`, `.eslintrc*`, `eslint.config.*`, `.eslintignore`, `biome.json`, `biome.jsonc`, `.prettierrc*`, `prettier.config.*`, `.prettierignore` and `bunfig.toml`; and `package.json` when its `scripts` or a tool's settings block in it (`eslintConfig`, `prettier`) changes, not for a dependency. The gate's command here is [package.json L6](https://github.com/brindlewick/postmaster/blob/8157c7a/package.json#L6). `.postmaster/project.toml` is not one: a run's checks are recorded at dispatch. The listing names the file and shows its diff, and an approval covers the file as it stands at the head. A new name is one entry. (C2, C10, D6, D8)
- The record: an approval names the run, the switch-off's identity from the third note and the user's words, and is written through `run log-action <dispatch> postmaster …`, so it lands in the run's `actions.jsonl` and the project's `ledger.jsonl` ([log-action.ts L1-L37](https://github.com/brindlewick/postmaster/blob/8157c7a/scripts/log-action.ts#L1-L37)). The verb set is fixed and enforced (L45-L46); `spec-review` is the precedent for a detail that carries the user's words (L16-L18). A refusal is recorded the same way. (C7, C9, D3)
- Stage F ([postmaster.md L455-L631](https://github.com/brindlewick/postmaster/blob/8157c7a/skills/postmaster/postmaster.md#L455-L631)): the new call runs after step 1's verification and before step 2's landing route, for every run, whatever `MERGE_AUTHORITY` says. On held, the postmaster puts the list to the user with the card, writes the question to `.waiting-on-user`, and waits; on the word it records it and asks the new call again. A missing reason or a refusal takes the withhold path step 1 already uses. A run pinned before this change has no list on its card, and its branch is still checked. [#266, Runbooks hold no code: each step is one call to a postmaster script](https://github.com/brindlewick/postmaster/issues/266) changes how runbook steps are written; this step is one call either way. (C6, C8, C9, C10, D1, D2)
- The coachman, in Stage 3 before step 4 writes `card.md` ([coachman.md L1000-L1049](https://github.com/brindlewick/postmaster/blob/8157c7a/skills/postmaster/coachman.md#L1000-L1049)): it runs the new call through `<tool>`, removes any switch-off it can fix, gives each one it keeps its reason, and puts the list on the card. If the list joins the block `card-block` renders, `card-results` and `card-findings` must still match the card of a run pinned before this change. (C5, D9)
- `scripts/landing.ts`, `skills/postmaster/coachman.md` and `skills/postmaster/postmaster.md` are in the coachman contract, so the branch needs a clean fixture run before it merges ([fixture runs](https://github.com/brindlewick/postmaster/blob/8157c7a/wiki/concepts/fixture-runs.md)). (C11)
- #260 adds a lint rule at error. Its tests plant switch-off text in strings, which C3 keeps off the list; its change to `.oxlintrc.json` waits for one word under D6. (C3, D6, D10)
