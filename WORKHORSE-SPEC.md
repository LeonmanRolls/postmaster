# Workhorse spec: 266 Runbooks hold no code: each step is one call to a postmaster script

## Problem / feature

Postmaster's runbooks hold shell code that agents copy and run. The coachman's review round alone has about a hundred lines of it, with loops over lanes, conditions and variables. The code has no tests, an agent can copy it wrong, and every leg reads it. It breaks where shells differ: [#217, Postmaster's flow runs on macOS, shown by a fixture run on a Mac](https://github.com/brindlewick/postmaster/issues/217) fixes four of its lines for zsh. The project's own rule puts deterministic work in scripts, and in the ticket session of [#260, A check refuses new Linux-only constructs in the scripts and runbooks](https://github.com/brindlewick/postmaster/issues/260) the user decided that the runbooks hold no code, so that the linter can read it (D1).

A runbook here is a document agents follow: the agents' instructions at the root of the repository and the documents of postmaster's skills (D5). Shell syntax means variables, substitutions, pipes, redirections, chains of commands, loops and conditions.

Done: each step an agent runs from a runbook is one call to a postmaster script, whose exit status and output are the step's result. The runbooks get shorter, and a review round is three calls (D7). Tested TypeScript does what the removed code did, runs behave as before, and the gate refuses code that comes back.

## Acceptance criteria

1. The gate fails when a code block in a runbook holds anything but calls to postmaster's scripts, one to a line.
2. The gate fails when a command in a runbook, in a code block or in the text, holds shell syntax.
3. Each refusal names the file, the line and what it found.
4. The check reads exactly the agents' instructions at the root of the repository and every document of postmaster's skills.
5. Once this lands, the gate passes on main.
6. Scripts with tests beside them do the work the removed code did, with the same records, output and stops.
7. The harness adapters document no longer repeats the launch and resume command lines that the launch script runs.
8. A change to the code that took over the runbooks' steps counts as a change to the coachman's contract.
9. A fixture run from the branch scores clean.

## Decisions

- **D1 (given by the user)** The runbooks hold no code: their shell steps move into scripts, which the linter reads. Why: checking the shell where it is would only work around code that should not be there. Instead of: a check that reads the runbooks' shell.
- **D2 (proposed)** A code block in a runbook holds only calls to postmaster's scripts. Why: anything else in a block is code that no test or linter reads. Instead of: also allowing git, gh or reading a file there.
- **D3 (proposed)** The text may still name a single command without shell syntax, such as a git command or a login the user runs. Why: naming a command is description, and agents commit and merge with git themselves. Instead of: refusing every command in the text, which would forbid naming git.
- **D4 (proposed)** A step that only reads a file names the file, and the agent reads it with its own tools. Why: agents read files without a shell, and a script that only prints a file has nothing to test. Instead of: a script that prints the machine's configuration.
- **D5 (proposed)** The check reads only the documents agents follow. Why: that is where steps are written. Instead of: also the README and the wiki, which people read and no agent runs steps from.
- **D6 (proposed)** The harness adapters document stops repeating the launch and resume command lines that the launch script runs and prints. Why: two copies drift, and nothing checks that they agree. Instead of: rewriting them in words or as a table, which would still repeat the script.
- **D7 (proposed)** A review round is three calls: cut, launch and wait, harvest. Why: the coachman acts between them, fixing a failed check after the cut and triaging after the harvest, and runs a wait cut short again alone. Instead of: one call per round, which would cut the round again when only its wait was cut short.
- **D8 (proposed)** The code that takes over the runbooks' steps joins the coachman's contract. Why: a change to those steps needs a fixture run today, and moving them into scripts must not drop that. Instead of: leaving it out, so that a change to the review round would land on the gate alone.
- **D9 (proposed)** It lands after #217. Why: #217 changes the same review steps and adds a test that runs them in bash and in zsh, which this change removes, having left it nothing to run. Instead of: landing first, which would make #217 rework both mid-run.

## Out of scope

- Steps in words with no shell syntax, even where a script could do them. More of the coachman's work by script, and its runbook split by leg, are ideas of [#265, A fixture run finishes in about an hour without proving less](https://github.com/brindlewick/postmaster/issues/265).
- Checking the new TypeScript for Linux-only constructs: #260.
- The README, the wiki, the archived trials, the fixture app, and the blind acceptance tests that runs write.
- Changing what any step does.

## Direction

Linux and macOS, in the project's TypeScript, each new script run like the others. It changes the coachman's steps, so it lands only after a fixture run from its branch scores clean, and after #217 (D9). It does not wait for #260, nor #260 for it. [#251, A booking clerk prepares every ticket that is not ready to run](https://github.com/brindlewick/postmaster/issues/251) also edits these runbooks; whichever lands second carries the other's changes.

### Checks

"The check" is the new gate step that reads the runbooks. "Planted" means one line added to a scratch copy of a file the check reads, or to a fixture its test writes; nothing is planted in the worktree. Lines are at 5c58c83, main after [#218, Every script runs as its TypeScript file, with no .sh wrapper left](https://github.com/brindlewick/postmaster/issues/218) and #217 landed, so every call is `scripts/run <name>`.

- **C1** Planted alone in an `sh` block: `git -C <repo> worktree prune`, `cat ~/.postmaster/config.toml`, `bun test scripts/wiki-lint.test.ts`, `cd <wt> && codex exec --json` → exit 1 naming it; removed → exit 0. Planted and not refused: `<tool>/scripts/run front-door "<harness>" "<model>" "<cwd>" <yes|no> <target>`, a trailing `#` comment, a `\` continuation, an optional `[--workaround "<what>"]`, and `-- <tool>/scripts/run runs-watch <runs>` or `-- <interactive form>` after `host run` or `host spawn`. **At the base:** `scripts/run skill-refs` exits 0 on a copy of `coachman.md` with the first two planted, and `wiki-lint` reads only the wiki; a prototype of the rule refuses 104 of the 175 non-blank lines in the `sh` blocks of the files C4 names.
- **C2** Planted alone, on a script call in an `sh` block and as a command in the text: a variable (`$NAME`, `"$TARGET"`, `NAME=value`), a substitution (`$(…)`, backticks), a pipe, a redirection (`>`, `>>`, `<`, `2>&1`, a here-document), a chain (`&&`, `||`, `;`), `&`, and a loop or condition (`for`, `while`, `if`, `case`) → each refused. ### Technical notes

- The check runs in the gate's check line ([package.json L6](https://github.com/brindlewick/postmaster/blob/5c58c83/package.json#L6)) beside `skill-refs` and `wiki-lint`, as a script with its test beside it; extending `skill-refs`, which already walks the runbooks for script paths, is as good. It reads `AGENTS.md` (`CLAUDE.md` is a link to it) and every `.md` under `skills/`, and nothing else. A block marked `sh`, `bash`, `zsh`, `shell` or `console` holds steps; a block in another language or none is a template or a format, and its lines are read like the text. (C1, C2, C3, C4, C5, D1, D2, D3, D5)
- A step line is blank, a `#` comment, or one call whose program is `scripts/run`: bare in `AGENTS.md`, else under `<tool>/` or another checkout's placeholder, such as `<checkout>/`. Continuations are joined. Placeholders in angle brackets (`<yes|no>`, `<the spec commit from spec-review.md>`), quotes, optional arguments in square brackets, a trailing comment, and `--` followed by a command are part of a call, and `run-meta run-pinned <dispatch> <name> …` is one call. [hosts.md L51-L52](https://github.com/brindlewick/postmaster/blob/5c58c83/skills/postmaster/hosts.md#L51-L52) writes alternatives as `launch|resume|…` and `[--role lane|coachman|reviewer]`: write them one form to a line, or as a placeholder. (C1, D2)
- A text command is an inline code span that starts with a script path, a program name followed by an argument, or a placeholder for a command (`<gate>`); a value, path, format or entity is not one. Where the check cannot tell a span from a command, reword the span and keep its meaning. The base's 16 text commands with shell syntax, and what each becomes: (C2, C5, D3)
  - `"$TARGET"` at [SKILL.md](https://github.com/brindlewick/postmaster/blob/5c58c83/skills/postmaster/SKILL.md) L136, L141, L143 and L168, with `$RUNS` and `$TARGET_ROOT` in its blocks and text: placeholders such as `<target>` and `<runs>`.
