# Workhorse spec: #170, The coachman writes one spec that every workhorse implements, and the user reviews it once

## Summary

The planning stage drops per-workhorse specs. The coachman writes and commits one spec for the ticket, the postmaster opens a spec session in which the user works on it with an agent, and on the user's word every workhorse implements from that one spec in blinkers, still free to choose the code. Every script this ticket writes or changes is TypeScript run by Bun. The two existing scripts it changes are copied unchanged from the port in #109 ("Rewrite the scripts in TypeScript, run by Bun") at commit `b8e5e6485f77`, and the change is made in the TypeScript, so #109's later merge meets the same files.

The ticket gained criterion 8 after this run's waybill was written. It is part of the contract:

> 8. At the spec pause the postmaster starts an interactive spec session for the user: on the postmaster's own harness, model and effort, named for the ticket, in the project's space, with an editor link to the spec and the context it needs (the ticket, the lanes' drafts if any, and the user's standing preferences). The user and that session work on the spec together, the user tells the postmaster when it is ready, and the postmaster then records the approval and resumes the run.

## Technical context

- **Language and version**: TypeScript run by Bun for every script this ticket writes or changes; bash only in the two-line wrappers that run them; markdown for runbooks and wiki pages
- **Dependencies used or added**: none. At run time the TypeScript imports only Bun's built-ins and Node's standard modules. `package.json`, `bun.lock`, `tsconfig.json`, `.oxlintrc.json`, `lint/` and `biome.json` stay as they are: #109 and #158 own them
- **Testing**: the loop under Showing each criterion: every criterion's check on a scratch run, then the run's checks, `<tool>/scripts/verify.sh run .`, and `bun test scripts/`. The run's checks are the waybill's gate, in which `scripts/spec-decisions.sh --self-test` and `scripts/spec-review-link.sh --self-test` run the controls the copied scripts carry inside them; `bun test scripts/` runs the tests beside the scripts, where this ticket's new controls live. A fixture run scores clean before merge, its spec signed off by the postmaster
- **Constraints**: every script this ticket writes or changes is TypeScript run by Bun, in a functional style, a pure core with side effects at the edges; new tests sit beside their script as `<name>.test.ts`, while tests a copied file carries inside it stay there; copied files change only where this ticket needs them to; a run dispatched before this change keeps its per-workhorse specs through the tool it is pinned to; workhorses stay in blinkers; the spec stays at the template's level; deterministic work lives in scripts, and every count has a positive and a negative control; nothing in the repository names the user, the machine or the user's preferences

## Decisions

- **The copy from #109.** Each workhorse's first commit, on its own, copies these files unchanged from commit `b8e5e6485f7719f0afacf3a2def843e53ee8697c` (`git show b8e5e6485f77:<path>`), which the waybill allows since it is not another lane's work: `scripts/spec-decisions.ts` and `scripts/spec-decisions.sh`; `scripts/spec-review-link.ts` and `scripts/spec-review-link.sh`; `scripts/lib/paths.ts`, `scripts/lib/proc.ts`, `scripts/lib/selftest.ts` and `scripts/lib/text.ts`, which those two import; and `bunfig.toml`, which the wrappers read. Contents and file modes are unchanged. At that commit both scripts carry their tests inside them, so there is no test file to copy. The coachman's hand-off names the copied files and the commit.
- **The change is made in the TypeScript.** In later commits, a workhorse changes the two copied `.ts` files only where this ticket needs it, and never edits `scripts/lib/`, `bunfig.toml` or the wrappers. Controls a copied script carries inside it stay there, updated only where this ticket's change breaks them. This ticket's new controls go in `scripts/spec-decisions.test.ts` and `scripts/spec-review-link.test.ts` beside the scripts.
- **Merging with #109.** Whichever branch merges second keeps #109's versions of the copied files and applies this ticket's changes to them again; those changes are exactly the commits after the copy. `scripts/lib/` and `bunfig.toml` take #109's side, and a copied file that #109 has since removed goes. Controls this ticket changed inside a copied script move with #109's other controls into its test file.
- **Review of the copy.** The copy is #109's code. It is checked only by comparing it with `b8e5e6485f77`, and review covers this ticket's commits after it.
- **No other existing script changes.** Changing one would mean copying its port too.
- **The new script.** `scripts/spec-session.ts`, with `scripts/spec-session.test.ts` beside it and a two-line wrapper, `scripts/spec-session.sh`, in the same form as the copied ones, so Bun never reads a project's `bunfig.toml` or `.env`. It may use the copied `scripts/lib/` modules. #109 has no file of that name.
- **Where the one spec lives.** `WORKHORSE-SPEC.md` at the synthesis worktree root, committed on the ticket branch before implementation. Its first commit is the record of intent and is never rewritten. For review, the coachman copies it to `<dispatch>/spec-review/WORKHORSE-SPEC.md`, a folder that holds nothing else, so an editor opened on the folder shows only the spec. On approval, the coachman commits the approved spec at each workhorse worktree root, and each lane reads its own copy.
- **Workhorses are not launched in the planning stage.** The coachman writes the spec alone. A workhorse is first launched after approval, to implement. A changes round is the coachman revising the one file and pausing again; there is no harvest of specs and no per-lane revision.
- **Decision words stay `approved|changes|dropped`.** `dropped` now means the run stops, not that one workhorse leaves it. `log-action.sh`'s validation and the audit language stay as they are, and the runbooks say what `dropped` means.
- **`spec-decisions` records one spec.** `record` takes no lane: one `## spec` stanza with `decision`, `commit` and `words`, as today. `count` prints `approved 0|1` and `changes 0|1`. A decisions file in the per-lane shape is counted as before, so an older run's file is never misread.
- **One approved spec is the bar.** The two-approved bar goes. A `dropped` decision stops the run, and the run says why.
- **Manifest.** On approval, `lanes.<lane>.spec_commit` is set to the approved synthesis commit on every implementing lane, so audit code that reads that field keeps working. No new top-level key.
- **Review package.** `spec-review.md` holds one entry: the spec's commit, the link, and the path of the copy. A revised spec is a new entry at its new commit, and the copy is refreshed from it. `.spec-review-ready` is unchanged.
- **Stage timings.** The `planning` stage stays between `bootstrapped` and `workhorses-running` and spans drafting through the last decision, the spec session included. `stage.sh` needs no change.
- **Template level.** The template gains one sentence: the spec is what to build, the decisions that matter and the tests, not the code. No new section.
- **The spec session starts at the pause.** At `.spec-review-ready`, in a run with a person to ask, the postmaster runs `spec-session.sh brief <dispatch>`, which writes the session's brief to the run's directory. It then starts the session with `host.sh spawn`, rooted in the project so it opens in the project's space, in the interactive form `harnesses.md` gives for the harness, model and effort the run recorded for `team.postmaster`. The session is named and labelled `<ticket name> · spec`, the ticket name coming from `host.sh name <dispatch>`. The postmaster sends it a one-line prompt to read the brief, and writes `.waiting-on-user` naming the session and the link. With no session host (`spawn` exits 3), the postmaster puts the spec to the user in its own conversation, as today. A fixture run gets no session.
- **What the session is given.** The brief holds the ticket as the waybill carries it; the editor link and the copy's path; the lanes' drafts by commit where the run has any, or a line saying there are none; the user's standing preferences; and the path of its runbook, `<tool>/skills/postmaster/spec-session.md`. The preferences are copied word for word from an optional `preferences.md` beside the machine config (`~/.postmaster/preferences.md`). Without that file, the brief says none are set. The brief is never committed.
- **What the session may do.** It edits only the copy. It commits nothing, and never resumes, stops or messages a run or another session. The user may comment in the file with `//` lines or inside `/* */`, and the session answers each comment and revises the text. When the user says the spec is ready, the session removes the comments, checks that the text meets every acceptance criterion, and tells the user to tell the postmaster. Nothing in the spec may identify the user or the machine.
- **Approval commits the text the user approved.** On the user's word, the postmaster runs `spec-session.sh approve <dispatch>`. If the copy differs from the committed spec, the script commits the copy as `WORKHORSE-SPEC.md` in the synthesis worktree, as a new commit; otherwise it commits nothing. It refuses when the synthesis worktree holds any other change. It then records `approved` at the resulting commit through `spec-decisions` and prints the commit. The postmaster removes `.waiting-on-user` and `.spec-review-ready` and resumes the run once.
- **Changes in words, and stops.** Changes the user gives the postmaster in words are recorded as `changes`; the coachman revises the spec and pauses again, and the revised spec goes to a spec session the same way. A stop is recorded as `dropped` with the user's words, and the run stops.
- **The session's tab.** It is left for the user to close. Closing a spawned session needs a change to `host.sh`, which would mean copying #109's port of it, so it waits.
- **Editor link.** In `planning.review_link`, `{path}` becomes the absolute path of the folder that holds the spec under review, as `{path}` in `ship.review_link` is a folder: code-server opens folders, not files. With no template, the link is the spec file's path, as today. The template must still contain `{path}`, so `setup.sh` needs no change.
- **Logging.** Starting the session is a `dispatch` line with the target `spec-session`. The approval is the `spec-review` line that `spec-decisions` writes, and a commit of the approved text is a `note`. `log-action.sh` gains no verb.

## Showing each criterion

_How each workhorse checks its own work. This section and its loop follow #179 ("A workhorse shows every acceptance criterion working, and keeps at it until it can"), whose change to the template is still in review._

**The loop.** Work in passes. In each pass, run every check below as written and fix what fails. When every check shows its criterion working, run the run's checks, `<tool>/scripts/verify.sh run .`, and `bun test scripts/`; a failure there means another pass. Stop when one pass is clean. You may add checks of your own, but never drop or weaken one here. If you are genuinely stuck, stop and write `WORKHORSE-BLOCKED.md` saying what blocks you. Keep each check's transcript, meaning the command, its output and its exit, under `.postmaster/verify/` in your worktree, which git ignores. In `WORKHORSE-SUMMARY.md`, add `## Evidence`: for each criterion, the transcripts from the last clean pass, or `not shown: <reason>`. Running `verify.sh run .` just before the summary stays the last step.

**The scratch run.** The checks run against a scratch run under `.postmaster/verify/`. It has a run directory shaped like a real one: its `run.json` records `planning.review_link = "https://code.example/?folder={path}"` and a `team.postmaster`, its manifest names two lanes, and its `brief.md` carries this ticket under `## Ticket`. It has a scratch git repository as its synthesis worktree, two more as workhorse worktrees, and a scratch machine config directory, reached through `POSTMASTER_CONFIG`. Every command a runbook names runs exactly as the runbook writes it, with only its paths filled in.
