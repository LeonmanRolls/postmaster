## Problem / feature

Tickets are now prepared with the user before they run: one document is both the ticket and the run's spec, and the user signs it off once. Nothing in the flow starts that preparation. The postmaster launches each such session by hand, and it can still dispatch a ticket nobody prepared. A run then pauses for the user to review a spec the coachman writes, so the same work is reviewed twice. The user's word on 2026-10-03: preparing tickets is a role of its own, filled by the strongest model they can afford; the postmaster starts a session for it when the user asks it to implement a ticket that is not ready; and a ready ticket is the run's spec, so the coachman writes none. Done: the booking clerk prepares every ticket with the user before it runs, and a run goes from dispatch to the ship card without a second review.

## Acceptance criteria

1. The flow calls the role that prepares a ticket with the user the booking clerk, wherever it names or lists its roles.
2. Setup asks which harness, model and effort the clerk runs on, and the config keeps the answer, as for the postmaster.
3. A script says whether a ticket is ready, and names each reason when it is not.
4. The clerk marks a ticket ready when the user says it is.
5. When the user asks the postmaster to implement a ticket that is not ready, alone or in a stream, it starts a clerk session for it instead of dispatching it.
6. The postmaster never dispatches a ticket that is not ready.
7. A ticket the clerk has marked ready is dispatched as soon as the postmaster has room for another run, with no further word from the user.
8. On Herdr, a clerk session opens in a new tab of the project's space, named with the ticket's number and title, such as "#2, Fix the list".
9. A clerk that the user starts from a session of their own, on whatever model it runs, follows the same instructions as one the postmaster starts.
10. Whatever harness it runs on, the clerk tests each draft on a fresh reader, another model given only the plain part and the code, and says when it cannot.
11. The coachman writes no spec of its own: the workhorses implement from the ready ticket.
12. A run goes from dispatch to the ship card without pausing for the user to review a spec.
13. Before any workhorse starts, the coachman checks that the ticket's premises still hold at the run's base.
14. When a premise no longer holds, the run stops before any workhorse starts, and the question goes to the user.
15. The parts of the flow that served only the spec review are removed, except what an older run needs to finish.
16. A run dispatched before this change finishes the way it started, its spec review included.
17. A fixture run from this change's branch scores clean.
18. The fixture score fails a run that started a workhorse before checking the ticket's premises.

## Decisions

- **D1 (given by the user)** The role is called the booking clerk, the clerk for short. Why: a ticket is what a booking office issues, so the name fits the flow's coaching words. Instead of: "ticket session".
- **D2 (proposed)** A ticket is ready when it passes both ticket checks and carries a ready mark. Why: the checks show the ticket is well formed, and only the mark shows the user signed it off. Instead of: the checks alone, which a draft nobody reviewed can pass.
- **D3 (proposed)** The ready mark is a label named "ready", shown with the ticket on every kind of tracker. Why: the trackers the flow reads all keep labels, and the blocked mark already works this way on the board. Instead of: a new column on the board, which every existing board would need added.
- **D4 (proposed)** A clerk opened on a ready ticket takes its mark off until the user signs it off again. Why: a ticket being changed is not ready to run. Instead of: keeping the mark while it changes, or taking it off at any edit, the user's own included.
- **D5 (proposed)** The user's sign-off counts as their word on the ticket's turnpikes. Why: the turnpikes are in the part the user signs off. Instead of: asking about them again at dispatch.
- **D6 (given by the user)** No working limit applies to clerk sessions. Why: a clerk starts only when the user asks for one. Instead of: a limit of three sessions at once.
- **D7 (given by the user)** The postmaster starts a clerk only when the user asks it to implement a ticket that is not ready. Why: the user chooses which ticket to prepare next. Instead of: the postmaster starting clerks on its own for every ticket that is not ready.
- **D8 (proposed)** The postmaster no longer drafts a ticket's missing parts itself; the clerk does, with the user. Why: one role prepares tickets with the user, in one place. Instead of: keeping the postmaster's own repair step beside the clerk.
- **D9 (proposed)** The clerk is a skill of its own, which the user starts by typing /clerk and a ticket number, and which the postmaster's launch uses too. Why: one set of instructions serves both ways in. Instead of: a runbook inside the postmaster's skill, reached only through a brief the postmaster writes.
- **D10 (proposed)** With no session host to open a tab in, the postmaster asks the user to start the clerk themselves. Why: the clerk needs a person to talk to, and a session started without a terminal has none. Instead of: a clerk with no terminal, answered by resume.
- **D11 (proposed)** A machine set up before this change starts no clerk until the user answers the postmaster's question about it, and setup adds the answer to the config. Why: the user wants their strongest affordable model here, not a quiet fallback. Instead of: falling back to the postmaster's model.
- **D12 (proposed)** The fresh reader runs as one of the configured lanes, on a model other than the clerk's, started the way the coachman starts a lane. Why: that works the same on every harness and needs no new setting. Instead of: a harness's own helper, which is quicker but which not every harness has.
- **D13 (proposed)** The clerk shares its draft as an editable document where its harness can publish one, and otherwise as a link built from the editor link the user set for spec reviews. Why: the user reads drafts on a phone, and only some harnesses can publish a document. Instead of: allowing only a harness that can publish one.
- **D14 (proposed)** The workhorses get the ticket in their brief, and no copy of it is committed on any branch. Why: the brief already carries the ticket word for word, and a committed copy must be taken out again before landing, which was once missed. Instead of: committing the ticket as a spec file in each worktree.
- **D15 (proposed)** The coachman writes its own acceptance tests from the ticket's checks while the workhorses run, before it looks at their work. Why: the checks already say how each criterion is shown, and writing the tests alongside costs the run no time. Instead of: writing them before the workhorses start, which would delay every run.
- **D16 (proposed)** A premise is anything the ticket says about the code; it still holds when that code has only moved, and fails when the code has changed or is gone. Why: most changes to a file leave what a ticket says about it true. Instead of: failing whenever a file the ticket names has changed.
- **D17 (proposed)** When a premise fails, the user either rules that the run goes on, or has the postmaster abandon the run and send the ticket back to the clerk. Why: the user signed the ticket off, so only they can say whether it still stands. Instead of: the coachman correcting the ticket on its own.
- **D18 (proposed)** The postmaster handles an older run's spec review from that run's own copy of the tool. Why: every run already keeps its own copy, so the current version need not keep the old steps. Instead of: keeping the spec review steps in the current version for older runs.
- **D19 (proposed)** The fixture tickets become ready tickets, filed already marked ready. Why: a fixture run has no person to sign a ticket off, as it has none to approve a spec today. Instead of: letting a fixture run skip the readiness check.
- **D20 (given by the user)** A ticket marked ready is picked up as soon as the postmaster has room for another run. Why: the user's sign-off is the go-ahead. Instead of: dispatching it only when the user says so again.
