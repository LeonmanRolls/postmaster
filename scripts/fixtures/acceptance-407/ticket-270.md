## Problem / feature

Every run sends its ticket to two workhorse lanes, then has the coachman compose one result from their work. This is synthesis mode, and it is the only mode there is. The audit of the last three days of runs ([#257](https://github.com/brindlewick/postmaster/issues/257)) could not say whether the workhorse lanes are needed, because no run has ever had a single implementer.

This ticket adds single-thread mode, in which the coachman writes the change itself and no workhorse lane runs. What happens once the change is written stays as it is: the reviews, the gate and the card. A setting in the machine's configuration tells the postmaster which mode to dispatch in, or to alternate between the two, and a mode the user names for a ticket wins. Every run, in either mode, follows the same rules for its acceptance tests. Done means a ticket can run in either mode, each run says which mode it ran in and why, and a fixture run in each mode scores clean. [#271](https://github.com/brindlewick/postmaster/issues/271) later looks at the runs' review rounds by mode.

## Acceptance criteria

1. A setting in the machine's configuration names the mode the postmaster dispatches in: synthesis, single-thread or alternate.
2. With no setting, the postmaster dispatches every run in synthesis mode, as it does today.
3. Under alternate, each ticket of a project gets the mode the project's previous run did not have.
4. A mode the user names for a ticket wins over the setting.
5. A run's record keeps its mode, whether the mode came from the setting or from the user, and the setting's value at dispatch.
6. In single-thread mode no workhorse lane starts, and the coachman writes the change itself on the run's own branch.
7. In single-thread mode the coachman commits the acceptance tests before any of the change.
8. In every run the acceptance tests test the feature at the boundary where it is used.
9. In every run the coachman may change an acceptance test later, for a good reason, in a commit of its own that says why.
10. In every run the coachman departs from one of the ticket's checks only on the postmaster's ruling.
11. In single-thread mode the coachman repeats build, check and fix until every one of the ticket's checks passes or it is stuck, as a workhorse does.
12. A single-thread run never enters the stage in which the workhorses run; the coachman writes its change in the synthesis stage.
13. Both modes have the same reviewers, the same rule for when review stops, the same gate and the same card.
14. No review brief names the mode.
15. A run's log and its card say which mode it ran in.
16. A leg whose waybill names a different mode from the run's record does not start.
17. The fixture score fails a run whose records do not match its mode, such as a single-thread run that started a workhorse.
18. A fixture run in each mode scores clean.

## Decisions

### Not covered by the acceptance criteria

- **D12 (proposed)** In single-thread mode the coachman still verifies and rules on each review finding, though the change is its own. Why: the reviewers' own reports are kept, so the comparison can count what it dismissed. Instead of: another model ruling on the findings in single-thread mode.
- **D13 (proposed)** The machine's configuration keeps its workhorse lanes, and a single-thread run leaves them unused. Why: synthesis mode needs them, and the reviewers can fall back on them. Instead of: a separate team for single-thread mode.

### Covered by the acceptance criteria

Each of these is stated by a criterion above; it is here for its reason and the alternative it beat.

- **D1 (given by the user)** Single-thread mode is the coachman writing the change itself, with no workhorse lane. Why: it is the cheapest test of whether the lanes are needed, and if it holds up it removes the whole lane layer. Instead of: one workhorse lane.
- **D2 (given by the user)** A setting in the machine's configuration decides the mode the postmaster dispatches in, with no fixed end. Why: one setting keeps the flow in one mode, or alternates it for as long as the user wants. Instead of: a trial of a fixed number of runs, or a line in each ticket.
- **D3 (proposed)** The setting takes synthesis, the default, single-thread or alternate, and under alternate each ticket of a project gets the mode the project's previous run did not have. Why: both modes then meet the same stream of work, project by project. Instead of: alternating across all projects at once.
- **D4 (proposed)** A mode the user names for a ticket wins over the setting. Why: the user may know that a ticket needs one mode. Instead of: the setting deciding every run.
- **D5 (proposed)** A single-thread run skips the stage in which the workhorses run, and the coachman writes its change in the synthesis stage. Why: the status never names work that is not happening, and the other stages keep their names and order. Instead of: keeping every stage, so the status says workhorses are running while the coachman writes the change.
- **D6 (given by the user)** In single-thread mode the coachman commits the acceptance tests before any of the change. Why: tests written before the code cannot be shaped by it. Instead of: writing them alongside the change.
- **D7 (given by the user)** In every run the acceptance tests test the feature at the boundary where it is used, as a person or, for a library, other code would use it: browser tests for a web app. Why: they show the feature as it will be used and leave its design free. Instead of: unit tests, which fix the design before it is written.
- **D8 (given by the user)** In every run the coachman may change an acceptance test for a good reason, in a commit of its own that says why, but departs from a ticket's check only on the postmaster's ruling. Why: reviewers see each change, and a check is part of the signed-off ticket. Instead of: fixed tests, or a coachman changing a check alone.
- **D9 (proposed)** In single-thread mode the coachman repeats build, check and fix until the ticket's checks pass, as a workhorse does. Why: a single implementer needs the workhorses' loop, and one pass would send known failures to review. Instead of: one pass, as the synthesis gets today.
- **D10 (proposed)** Review and landing are the same in both modes. Why: the modes should differ only in who writes the change, so that their review rounds can be compared. Instead of: a review shaped for each mode.
- **D11 (proposed)** No review brief says which mode a run is in. Why: a reviewer told that one model wrote the change alone may review it differently, which would skew the comparison. Instead of: telling the reviewers, so that they look harder at a change no second implementer wrote.
- **D14 (proposed)** The fixture score checks that a run kept its mode. Why: today a single-thread run that started a workhorse would still score clean, so the fixture runs would not show that the mode works. Instead of: a check by hand, once, in this ticket's fixture runs.

## Out of scope

- Changing the default mode, which may follow from #271's look at the runs.
- A mode setting for each project: the setting is the machine's.
- Choosing which model writes the change in single-thread mode: the configured coachman does.
- The same loop for the synthesis in synthesis mode, and what the coachman does in either mode when it cannot make a check pass beyond showing it on its card. [#264](https://github.com/brindlewick/postmaster/issues/264) covers both.
- Acceptance tests in synthesis mode when the ticket leaves the interface to the workhorses: [#280](https://github.com/brindlewick/postmaster/issues/280) takes that up.
- A mode with one workhorse lane.
- Setting up a machine with fewer than two workhorse lanes.
- Changing the reviewers, their prompts or the models.

## Direction

This changes the coachman's steps, so it merges only after a fixture run in each mode scores clean. It does not wait for [#265](https://github.com/brindlewick/postmaster/issues/265), [#266](https://github.com/brindlewick/postmaster/issues/266) or [#268](https://github.com/brindlewick/postmaster/issues/268): whichever lands first, the others merge it in. Runs already in flight keep the version they started on. It must work on Linux and macOS.
