Ticket #332

Sessions the flow opens for the user run the harness as the pane's own process, so the chat app lists them

Problem / feature

The user's chat app lists a session only when the agent is the pane's own process. A booking clerk that the postmaster opens runs instead as the child of a small helper shell, which loads the clerk's environment file and then waits for the agent to finish. The app shows such a pane as a plain terminal, so the user cannot answer a waiting clerk from a phone. One clerk waited more than a day for that reason. A postmaster session opened in a pane has the same problem whenever its role has an environment file.

Done: every session the flow opens for the user to talk to runs its agent as the pane's own process, with the same environment as today, and the launches that run without the user work exactly as they do now.

Priority: high, on the user's word, because until it ships the user cannot answer a waiting clerk from a phone. Its clerk started at once, ahead of the queue.

Acceptance criteria

  1. A booking clerk or a postmaster that the flow opens in a pane runs its agent as the pane's own process, so the chat app lists it.
  2. The agent in such a session starts with the same environment as today, its role's environment file included.
  3. The launches that run without the user, which are the workhorses, the reviewers, the coachmen and a headless postmaster, start and end exactly as they do today.
  4. A fixture run from this branch scores clean.

Decisions

Covered by the acceptance criteria

Each of these is stated by a criterion above; it is here for its reason and the alternative it beat.

  • D1 (proposed) Only the sessions opened for the user change; the launches that run without the user keep today's helper shell. Why: changing the shared helper would also change how those launches record an agent that was killed. Instead of: one change to the helper that every launch shares.
  • D2 (proposed) A session keeps loading its role's environment file, as today. Why: the file can hold what an agent needs to start at all, such as a provider key. Instead of: starting sessions through the session host's own agent start, which cannot load the file and exists on one host only.

Out of scope

  • Making the launches that run without the user visible in the chat app. They are not chat sessions.
  • Restarting the sessions that are running now. That is done by hand, one at a time.

Direction

It changes how the flow launches agents, which is part of the coachman's contract, so it merges only after a fixture run from its branch scores clean. It must work on Linux and macOS, and on both session hosts. The launches that run without the user share the same helper shell and must keep working exactly as now. #258 is open and changes the same launcher in other places; whichever lands second merges the other in.

Before this change, every launch with an environment file went through this helper. Its short bash script loads the file, then starts the agent with "$@", waits for it, and exits with the agent's status. Bash stays the pane's own process the whole time, and the agent runs one level below it.

The new helper ends with exec

sourcedExec keeps the old script's start and changes its end. Instead of starting the agent and waiting, the shell runs exec, which replaces the shell with the agent. The agent keeps the shell's process id and its place in the terminal.

To test this, a test has to see which process group the terminal is serving. The shared process module now reports that for every process, as terminal: the group the terminal hands its input to, or nothing when the process has no terminal.

On Linux the number is field 5 of the process's stat file. macOS has no such file, so the module asks ps for one more column, tpgid, and each column after it moves along by one. The minimum column count goes from 11 to 12 to match.
