### A1.1 Instance states and what stops an instance
- finding: A container instance goes stopped -> starting (`start()` called) -> running/not ready -> ready -> stopping -> stopped; an inactivity timeout, `signal()`, `destroy()`, a rollout or a process exit can stop it; `ctx.container.running` is true before the process accepts traffic.
- quote: "An inactivity timeout, `signal()`, `destroy()`, a rollout, or a process exit can stop the instance." (verbatim)
- source: https://developers.cloudflare.com/containers/concepts/architecture/ ; docs/containers/concepts/architecture.mdx@6e1b964 lines 21-48 ; read 2026-10-08

### A1.2 Idle timeout, DO API (`setInactivityTimeout`)
- finding: With `ctx.container`, the timeout is set per Durable Object instance with `setInactivityTimeout(ms)`; value > 0 and at most 6 hours (21,600,000 ms); the timeout measures how long the container runs after "its Durable Object becomes inactive"; with no timeout set Cloudflare stops the container "shortly after" the Durable Object becomes inactive; the setting is lost when the Durable Object restarts (e.g. after a deploy) and must be set again in the constructor.
- quote: "Without a timeout, Cloudflare stops the container shortly after the Durable Object becomes inactive." (verbatim)  ;  "A Durable Object that restarts, for example after a deploy, starts without one." (verbatim)
- source: https://developers.cloudflare.com/containers/api/durable-object-container/ ; docs/containers/api/durable-object-container.mdx@6e1b964 lines 380-443 ; read 2026-10-08

### A1.3 Idle timeout, `Container` class (`sleepAfter`)
- finding: `sleepAfter` defaults to "10m" (number of seconds or duration string); "Activity resets the timer"; incoming requests reset it automatically; background work (a scheduled task or long-running operation) must call `renewActivityTimeout()` to count as activity; `onActivityExpired()` fires "when the sleepAfter timeout expires with no incoming requests" and by default calls `stop()`; an override that does not stop the container makes the timer renew and fire again. `Container` class works only with the `default` policy.
- quote: "Incoming requests reset the timer automatically. Call this manually from background work, such as a scheduled task or a long-running operation, that should count as activity and prevent the container from sleeping." (verbatim)

### A1.8 Rollout modes and how to leave running instances on the old version
- finding: Three modes. Gradual (default): `rollout_step_percentage` default `100` if `max_instances` omitted or <2, else `[10, 100]`. ### A1.13 What keeps the fronting Durable Object (and so, for the DO API, the container) from being treated as inactive
- finding: Since 2026-06-19 active outbound TCP sockets and outbound WebSockets keep a Durable Object alive; since 2026-10-01 (default for compatibility date 2026-10-01 or later, or flag `durable_object_io_tasks_prevent_eviction`) pending service-binding requests, pending DO RPC/`fetch()` calls, `ctx.container.monitor()`, `waitUntil()` promises and pending `setTimeout`/`setInterval` also prevent eviction. Each pending operation keeps the DO alive for at most 15 minutes ("The limit applies to each operation, not to the total time in memory"); duration charges continue meanwhile. The lifecycle page lists the same set. So a held-open `exec()` through a DO RPC call or a `monitor()` call keeps the DO in memory for up to 15 minutes per operation. Whether that holds off the container's own `setInactivityTimeout` is stated only for `monitor()` (lifetime page, A1.15: "A pending `monitor()` call keeps the Durable Object in memory, so the inactivity timeout starts only after the Durable Object leaves memory"); for the other pending operations it follows from the definition of the timeout ("after its Durable Object becomes inactive") and is argued, not stated.
- quote: "Each pending operation prevents idle shutdown for up to 15 minutes. Starting another one later can extend the Durable Object's time in memory." (verbatim)
- source: https://developers.cloudflare.com/changelog/durable-objects/ (2026-10-01 entry) ; changelog/durable-objects/2026-10-01-pending-io-keep-alive.mdx@6e1b964 lines 9-27 ; changelog/durable-objects/2026-06-19-outbound-connections-keep-dos-alive.mdx@6e1b964 lines 9-26 ; docs/durable-objects/concepts/durable-object-lifecycle.mdx@6e1b964 lines 66-72 ; read 2026-10-08

### A1.15 [KEY] Sandbox lifetime page: what counts as activity, and that code inside the instance does NOT
- finding: For a Sandbox on the DO API, an instance keeps running while its Durable Object is active: handling a request, running an alarm, streaming a response, or holding an accepted WebSocket open (so an open terminal keeps it running "even when nobody types"). After the DO becomes inactive the instance runs on for the `setInactivityTimeout()` time (up to 6 h), then Cloudflare stops it. Code running inside the instance (a build, a test suite, an agent task) is NOT activity: "If no requests arrive, the instance stops when the inactivity timeout ends, even while a build, a test suite, or an agent task still runs inside it." The documented workaround is a Durable Object alarm that runs more often than the timeout and checks the work (the background-processes guide uses an alarm every minute). A pending `monitor()` keeps the DO in memory, so the timeout then starts only after the DO leaves memory, and `monitor()` then ends without reporting the stop.
- quote: "Code that runs inside the instance does not count as activity." (verbatim)
- source: https://developers.cloudflare.com/sandbox/concepts/lifetime/ ; docs/sandbox/concepts/lifetime.mdx@6e1b964 lines 34-42 ; read 2026-10-08 (page `reviewed: 2026-09-24`)
- strength: stated

### A1.16 [KEY] What stops an instance, and what the instance gets when the timeout ends
- finding: An instance stops when (1) the inactivity timeout ends, (2) the Worker calls `destroy()`, or (3) the main process exits (the entrypoint passed to `start()` or the image default command; every `exec()` process ends with it; `cloudflare/debian-trixie` default command exits at once, so examples run `sleep infinity`). On timeout expiry "every process in the instance receives SIGTERM, and Cloudflare stops the instance shortly after, whether or not the processes exit"; `destroy()` is immediate. Cloudflare does not wake the Durable Object when the instance stops (record stops via the "Run code when a sandbox stops" guide).
- quote: "When the inactivity timeout ends, every process in the instance receives `SIGTERM`, and Cloudflare stops the instance shortly after, whether or not the processes exit." (verbatim)
- source: https://developers.cloudflare.com/sandbox/concepts/lifetime/ ; docs/sandbox/concepts/lifetime.mdx@6e1b964 lines 50-64 ; read 2026-10-08

### A1.18 Which statement holds for which generation / policy (answer to the orientation question)
- finding: (a) "SIGTERM then SIGKILL after 15 minutes" holds for any platform-initiated stop of an instance, stated for the `default` policy rollouts, for host moves (FAQ), and generally ("When the platform is about to stop a container instance"). It is NOT how the inactivity timeout ends a sandbox: the Sandbox lifetime page says processes get SIGTERM and Cloudflare stops the instance "shortly after, whether or not the processes exit" (no 15-minute wait stated there). (b) A deploy does not restart running instances under `durable_object` policy (Sandbox SDK 1.0 and DO API). Under `default` policy a deploy that changes the image/instance type starts a rollout that does SIGTERM/15 min/SIGKILL; a deploy with no effective container change starts no rollout. (c) "Sleeps after 10 idle minutes" is the `Container` class (`default` policy) default `sleepAfter`; the DO API has no default timeout (stops "shortly after" DO inactivity unless `setInactivityTimeout` is set, max 6 h). (d) Disk is ephemeral under both; snapshots (beta) exist only under `durable_object` policy. A NEW project today: the docs steer to the DO Container API (`ctx.container`), and Sandboxes on Cloudflare use the `durable_object` policy (beta).
- quote: "A sandbox container uses the Durable Object scheduling policy, which is in public beta." (verbatim)

### A1.25 Held-open exec: what the docs let one conclude (argued, with the sources)
- finding: Three documented facts combine. ### A10.3 Arithmetic: one standard-4 instance for one hour (every step)
Inputs: standard-4 = 4 vCPU, 12 GiB memory, 20 GB disk (partials/containers/instance-types.mdx@6e1b964 line 8). One hour = 3,600 s. Rates per A10.1. A script in exact decimals gave the same figures as the hand arithmetic below.
- Memory (provisioned): 12 GiB x 3,600 s = 43,200 GiB-s; x $0.0000025 = $0.108.
- Disk (provisioned): 20 GB x 3,600 s = 72,000 GB-s; x $0.00000007 = $0.00504.
- CPU (active use only), two cases: (a) CPU fully busy on all 4 vCPU: 4 x 3,600 = 14,400 vCPU-s; x $0.000020 = $0.288. (b) average 25% busy: 14,400 x 0.25 = 3,600 vCPU-s; x $0.000020 = $0.072.
- Total at list rates before allowances: (a) $0.108 + $0.00504 + $0.288 = $0.40104; (b) $0.108 + $0.00504 + $0.072 = $0.18504.
- With the Workers Paid monthly allowances (25 GiB-hours = 90,000 GiB-s of memory; 375 vCPU-minutes = 22,500 vCPU-s; 200 GB-hours = 720,000 GB-s of disk): this one hour uses 43,200 of 90,000 GiB-s, 72,000 of 720,000 GB-s, and 14,400 (case a) of 22,500 vCPU-s, so the first such hour in a month is inside the allowances: $0 for Containers (excluding the $5/month plan fee, Workers, DO and egress). The allowances are used up after about 2.08 hours of standard-4 memory (90,000/43,200) in a month.
- Durable Object in front, same hour, if it stayed in memory the whole time: 0.125 GB x 3,600 s = 450 GB-s; x $12.50/1,000,000 = $0.005625 (less within the 400,000 GB-s monthly allowance).
