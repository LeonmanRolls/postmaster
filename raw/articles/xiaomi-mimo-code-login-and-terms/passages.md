### XMI1 H1 MiMo: how a headless run finds a key (read from source)

### XMI2 H1 MiMo: credential file path, field names and the whole-file env variable
- finding: Credentials are in auth.json in the data directory: ~/.local/share/mimocode/auth.json on Linux (macOS ~/Library/Application Support/mimocode/; Windows %LOCALAPPDATA%\mimocode\), all moved by the env var MIMOCODE_HOME. Written with file mode 0600. Entries are keyed by provider id with three shapes by field name: {type:"oauth", refresh, access, expires, accountId?, enterpriseUrl?}, {type:"api", key, metadata?}, {type:"wellknown", key, token}. The whole file can instead be supplied as JSON text in the environment variable MIMOCODE_AUTH_CONTENT, which is checked first on every read; MIMOCODE_CONFIG_CONTENT likewise carries config. Both variables are stripped from the environment of child processes the agent spawns, and an embedding host can inject credentials in memory.

### XMI7 H6 MiMo: storage and refresh of credentials (from source)
- finding: Auth is read on every call: `all()` first looks at the in-process injected value, then env MIMOCODE_AUTH_CONTENT, then re-reads auth.json from disk (no cache), so a key or login changed in the environment or file is picked up on the next read. The Xiaomi login stores a static API-style key with no refresh token and no expiry field (type "api"); the "oauth" shape with refresh/access/expires exists for providers such as OpenAI Codex and xAI. The provider table is rebuilt on a models-catalog refresh without disposing instances (commit #2603 "refresh model configuration without disposing instances"), which re-runs the env scan. The provider catalog is fetched from https://models.dev/api.json (override MIMOCODE_MODELS_URL / MIMOCODE_MODELS_PATH; MIMOCODE_DISABLE_MODELS_FETCH disables the fetch), cached under ~/.cache/mimocode, with a build-time snapshot as fallback.
