### OTH1 H1 pi: logins, headless
- finding: Credentials come from, in this order: a runtime --api-key, a stored auth.json credential, an apiKey in models.json, then the provider's environment variable or ambient cloud credentials; once a credential is stored for a provider it "owns" it and the environment is not consulted. auth.json lives at <agent-dir>/auth.json (agent dir default ~/.pi/agent, moved by PI_CODING_AGENT_DIR). Env vars are recommended for CI (examples: ANTHROPIC_API_KEY, OPENAI_API_KEY, XAI_API_KEY, GEMINI_API_KEY, META_API_KEY, XIAOMI_API_KEY, XIAOMI_TOKEN_PLAN_SGP_API_KEY). A stored key can be a command prefixed with ! that pi runs once per process. /login does OAuth (browser or device flow) or API-key entry; on a headless machine "paste the final redirect URL or authorization code back into Pi". pi supports print and JSON modes and RPC for automation, and ships a docs page on running it in Docker/sandboxes.
- quote: "Environment variables are useful in CI and anywhere Pi should not store the key." (verbatim, providers.md) ; "On a remote or headless machine, an OAuth callback may not reach the local process. When prompted, paste the final redirect URL or authorization code back into Pi." (verbatim, providers.md) ; "A stored credential owns the provider: ambient/env is consulted only when nothing is stored." (verbatim, code comment packages/ai/src/auth/resolve.ts)
- source: https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/docs/providers.md ; .../docs/models.md ; .../docs/configuration.md ; .../packages/ai/src/auth/resolve.ts ; read 2026-10-08 (repository text, curl of raw files)
- strength: stated

### OTH3 H1 pi (about Meta): how the Meta login really yields a key
- finding: The pi source documents Meta's flow: an RFC 8628 device authorization grant at https://auth.meta.com using the Muse Code CLI client id, giving an identity token that "is not accepted for inference"; pi exchanges it at https://api.meta.ai/muse-code/key for a Model API key that lives about a day (API_KEY_LIFETIME_MS = 24 hours) and re-mints when it expires; the identity token cannot be renewed (auth.meta.com "answers grant_type=refresh_token with 404 and issues no refresh_token"), so after it dies the user must sign in again. This is a third-party code comment about Meta's behaviour, not a Meta statement, but it matches the Muse launcher's use of the same endpoints. Consequence if true: the key is re-minted from the identity token, so a subscription-style login keeps working only as long as the identity token is accepted; its lifetime is not stated anywhere I read, and when it is rejected a human must repeat the device login. A dashboard-created META_API_KEY is a team key with no stated expiry (the auth page does not give a lifetime).
- quote: "minted keys live about a day" ; "The identity token itself is not renewable (auth.meta.com answers grant_type=refresh_token with 404 and issues no refresh_token)" (verbatim, code comments, packages/ai/src/auth/oauth/meta.ts lines 1-14, repository text)
- source: https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/ai/src/auth/oauth/meta.ts ; read 2026-10-08
- strength: shown (third-party source; Meta page does not state key lifetime)

### OTH5 H1/H3 pi: container and credential-substituting proxy patterns in pi's own docs
- finding: pi's containerization guide lists four patterns. Plain Docker passes credentials into the container (for example `-e ANTHROPIC_API_KEY`, with a named volume for container-local auth.json). Docker Sandboxes and NVIDIA OpenShell keep the real provider credential on the host or in the gateway and substitute it at a proxy, so the sandbox holds only a placeholder; for a Claude Pro/Max token the guide has the user generate it with `claude setup-token` on a machine with Claude Code and register it as a custom secret that the proxy swaps in for requests to one configured host. It warns not to mount the host's ~/.pi/agent (it exposes credentials) and not to run /login inside such a sandbox. This is pi's documentation of a credential-injection pattern, not a vendor endorsement of using a subscription token that way (see the Anthropic entry).
- quote: "Provider credentials remain on the host and are substituted by the proxy" (verbatim, containerization.md table) ; "Do not run `/login` inside the sandbox because that writes a real credential into it." (verbatim) ; "The sandbox receives an OAuth-shaped placeholder, which the proxy replaces only for requests to the configured host." (verbatim)
- source: https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/coding-agent/docs/containerization.md lines 9-14, 84-103, 151 ; read 2026-10-08 (repository text)
- strength: stated (in pi's docs)

### OTH6 H6 pi: refresh and storage
- finding: OAuth credentials refresh under a credential-store lock, re-checked under the lock so concurrent processes refresh once; the refreshed token is persisted before the lock is released; a minimum remaining validity of five minutes is required by default. Resolution runs per operation, so env or stored changes are seen on the next call. No silent fall back to the environment after a failed refresh.
- quote: "Refresh a stored OAuth credential under the credential-store lock and persist the result before the lock is released." (verbatim, resolve.ts doc comment)
- source: https://github.com/earendil-works/pi/blob/6fb2e7815167e6b19006fc526d1a5d0f5f998787/packages/ai/src/auth/resolve.ts lines 87-110 ; read 2026-10-08
- strength: shown

### OTH7 H1 grok: login, headless
- finding: `grok login` (browser OIDC, default, refreshable), `grok login --device-auth` (device code, "for headless or remote environments", refreshable), an external `auth_provider_command` in config (refreshable), and an API key via env var XAI_API_KEY or model.api_key in config (not refreshable). XAI_API_KEY is listed as "API key when not using browser/session login (CI and headless)." Headless: `grok -p`; permission flags --always-approve (alias --yolo) and Claude-compatible --dangerously-skip-permissions. Proxy: HTTPS_PROXY/HTTP_PROXY/NO_PROXY honoured.

### OTH11 H1 agy: login, headless
- finding: Interactive sign-in uses the OS keyring, else Google Sign-In (local browser, or on SSH an authorization URL to open elsewhere and a code to paste back). "Headless mode uses your cached credentials. Authenticate once with an interactive `agy` session first." A non-interactive run that is not authenticated exits with an "authentication required" error. The alternative for headless and CI is a Gemini API key: set modelProvider to gemini in ~/.gemini/antigravity-cli/settings.json and export GEMINI_API_KEY ("on its own has no effect"; read only from the environment, not from .env files). Enterprise routes: Google Cloud project, Workforce Identity Federation, Application Default Credentials (service-account sign-in). On Linux hosts without a D-Bus session bus (containers) the keyring is bypassed and credentials go to file storage.
- quote: "Headless mode uses your cached credentials. Authenticate once with an interactive `agy` session first." ("Headless mode uses your cached credentials." verbatim, two fetch-tool reads; "Authenticate once with an interactive `agy` session first." first read only -> paraphrase) ; "Setting a `GEMINI_API_KEY` environment variable on its own has no effect." (verbatim, docs/cli/install, two fetch-tool reads; the repo changelog line 461 independently describes the same three-step setup) ; changelog: "the CLI now bypasses the keyring when no D-Bus session bus is present (headless hosts and containers)" (verbatim, repository text line 648)
- source: https://antigravity.google/docs/cli/install ; https://antigravity.google/docs/cli/headless ; https://github.com/google-antigravity/antigravity-cli/blob/968f1170bd0e002e9d0914730975bc8a2cc65861/README.md and CHANGELOG.md lines 461, 493, 535-537, 648, 656 ; read 2026-10-08

### OTH14 H4 pi/Anthropic: subscription OAuth outside Claude Code
- finding: pi offers "Anthropic (Claude Pro/Max)" OAuth login. Anthropic's Claude Code legal page says OAuth is "intended exclusively" for subscription holders and "designed to support ordinary use of Claude Code and other native Anthropic applications", tells developers building products to use API keys, and says Anthropic "does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users". Whether a user running pi on their own machine with their own login counts as "third-party developers ... on behalf of their users" is not addressed; the page shows no date. (Claude Code itself is another helper's subject; recorded here only because pi can use this login.)
